## §B Filesystem persistence

### B1 — Preserve changed versions before removing live content

- **AC8; verified current-code defect; severity 4 / P1.** Diagnostics → Archive on a restored, edited entry. `web/server/knowledge/kb-store.ts:373` collects archived ids only; `:456–460` treats any matching id as proof the live version was saved. OLD archived + NEW live produces `completed-partial`, deletes NEW from live, and saves no NEW copy. Heuristic: error prevention; recovery cannot recover missing content.
- **Minimal change:** use content equivalence, excluding only archive-added metadata (`archivedAt`, `archiveReason`), to distinguish a genuine interrupted move from a changed version. Preserve all other fields, including unknown fields and nested content. If no equivalent archive copy exists, durably save the live version before removal; matching id alone is insufficient. Keep existing schema and outcomes where possible. Retain archive-before-live order and existing sentinel/ledger ordering.
- **Red-first:** in `kb-store.test.ts`, seed archived OLD plus live NEW with the same id; archive; assert both versions survive in archive and unrelated/corrupt live rows remain verbatim. Retry and assert no extra NEW copy. Keep identical-content interrupted-move test and add field-order variation/unknown-field cases. In `kb-decisions.test.ts`, assert ledger is written only after the matching NEW version is durable; failed live rewrite must remain recoverable.
- **Dependencies:** coordinate with B4 writer safety; do not claim concurrent-write safety from this fix alone.

### B2 — Treat corrupt nested reports as unavailable, never executable capabilities

- **AC8; verified current-code defect; severity 3 / P2.** `web/server/diagnostics/kb-analysis-store.ts:80–97` dereferences each signal without checking it is non-null; `signals:[null]` throws outside the JSON parse catch (`:116`). Missing finding entry and malformed memory pass the current guard. `kb-decisions.ts:46` then reads `report.memory?.findings.map`, which fails for `memory.findings=null`. Diagnostics load/decide becomes a server error instead of a recovery state. Heuristic: recognize and recover from errors.
- **Minimal change:** make the existing report boundary total for unknown JSON, validate every nested field consumed by status/cards/decision validation, accept supported optional fields, and return `report-invalid` for malformed supported-schema reports. Preserve explicit newer-schema handling. No schema migration or replacement storage layer.
- **Red-first:** table cases in `kb-analysis-store.test.ts`: null/primitive signals; missing or malformed entry; memory object with null/nonarray findings; malformed duplicate partner/merge-task structures; invalid numeric fields. Assert no throw and `unavailable/report-invalid`; valid existing report fixture remains available. Route/status test with the malformed report must yield recovery output and decision rejection with no append/pending/archive calls. Do not call malformed input a successful empty report.
- **Dependencies:** agree required nested shapes with existing report consumers and types; share this task with backend boundary owner.

### B3 — Recheck analysis exclusion after reading the request body

- **AC8; verified current-code defect; severity 3 / P2.** `web/server/routes/diagnostics-routes.ts:60–66` checks `isRunning()` before `await c.req.json()`. An analysis can start during slow body delivery, after which validate/apply still execute. Heuristic: error prevention and accurate system state.
- **Minimal change:** after body parsing, check running state immediately before the synchronous current-report/validate/apply section, returning existing 409 conflict without side effects. Retain the early check if useful. There must be no intervening await between the final guard and application. This addresses same-server scheduling; it is not a multi-process lock.
- **Red-first:** `diagnostics-routes.test.ts`: a deferred request body starts with running=false, switches running=true while pending, then resolves valid body. Expect 409; assert apply, afterDecisions and durable mutation dependencies never run. Also change report while awaiting and assert stale runId 409; retain ordinary success and initially-running tests.
- **Dependencies:** none; small standalone backend correction.

### B4 — Resolve the append/replace concurrency boundary before declaring AC8 data-safe

- **AC8; source-established race window, runtime reproduction still required; prospective severity 4 / P1 if reproduced.** `kb-store.ts:466–468` replaces an archive from a read snapshot without checking concurrent archive changes. `:471–475` checks live identity, then `atomic-write.ts:beforeRename → renameSync` leaves a cross-process scheduling window. Atomic rename makes one replacement indivisible; it does not serialize a read/modify/write against another process's append or another archive transaction. Synchronous JavaScript only excludes same-event-loop interleaving. Existing conflict test covers append **before** identity check, not after. Heuristic: error prevention.
- **First deliverable:** deterministic temporary-file regression with two independent processes and explicit barriers. A checks identity, B appends a distinct row and fsyncs, then A renames; assert B's row survives or A refuses before destructive replacement. A second case interleaves two archive snapshot reads/writes and asserts both saved versions survive. No sleeps as the synchronization mechanism. Until this fails in a controlled repro, retain the finding as a hypothesis with source evidence, not a reproduced production loss.
- **Minimal viable safe release:** if cooperative serialization cannot be established for every content writer, disable destructive Archive/prune application with an explicit recoverable unavailable/conflict result; keep read-only analysis and non-destructive decisions available. A lock acquired only by Diagnostics is not a fix for `/learn` or direct editor appends. A retry/checksum/additional stat is not atomic compare-and-swap.
- **Durable fix decision:** enumerate actual `/learn`, CLI prune, Diagnostics archive and other store writers first. If all can cooperate, use one KB-root cross-process transaction lock covering content load, archive durable replace and live durable replace, acquired by appenders too. Prefer a proven OS-held lock with release-on-process-exit; any sentinel lock needs identity-safe ownership/recovery and crash tests, not an unqualified timeout deletion. Keep existing atomic file helpers beneath this boundary and EC-8 archive recovery. No database/schema migration is justified. Arbitrary external writers cannot be made safe by a cooperative lock; document the boundary and keep destructive actions gated where it cannot be enforced.
- **Red-first/verifier:** the two barrier tests above, writer rejection/timeout with no mutations, process death releasing ownership, crash after archive but before live replacement recovering without content loss, and independent Bun-process tests on the deployed filesystem. Test `kb-health.ts prune` uses the same boundary. Physical iPhone testing provides no evidence for these invariants.
- **Dependencies:** requires explicit plan decision because it touches writer protocol beyond the assigned backend files. If chosen, writer inventory and red repro precede implementation, then B1 and concurrency tests close together. Do not grow this into a general persistence framework.
