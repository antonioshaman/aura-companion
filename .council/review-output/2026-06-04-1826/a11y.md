## P1 — Fix Now

### P1.new — `expect(listbox).toHaveFocus()` after open is still not asserted; the burndown's "fix P1.2" test pins dismissal, not the open-edge focus contract it claims to close

**File:** `web/src/components/ModelSwitcher.test.tsx:401-423` (new test "click-outside restores focus to the trigger when focus was inside the listbox") and `ModelSwitcher.tsx:169-182` (the rAF autofocus effect).

The first review's P1.2 said two things: (a) switch from `queueMicrotask` to `requestAnimationFrame`; (b) add a behavioural test that the listbox actually receives focus on open. The burndown shipped (a) — verified at `:179-181`. It did NOT ship (b): no test in the suite calls `fireEvent.click(trigger)` and then `await waitFor(() => expect(listbox).toHaveFocus())`. What it shipped instead is a test that **manually** calls `listbox.focus()` at `:414` ("jsdom doesn't implement requestAnimationFrame's paint-tick exactly, so call .focus() directly to model the post-rAF state") and then asserts dismissal restores focus to the trigger.

The skipped half is the producer side of the contract — that the rAF actually runs and the focus actually lands. The new test SIMULATES that state; it does not VERIFY it. A regression where the rAF call is dropped (e.g., a refactor that re-introduces `queueMicrotask` or removes the open-edge effect entirely) would leave the test green: the test fakes the post-rAF state regardless.

The standard JSDOM workaround for rAF in vitest is `vi.spyOn(window, "requestAnimationFrame").mockImplementation((cb) => { cb(0); return 0 })` — this flushes rAFs synchronously and lets `expect(listbox).toHaveFocus()` after `fireEvent.click(trigger)` actually pin the call site. The codebase precedent (CouncilToggle.tsx) uses rAF and presumably has a working pattern; mirror it.

**User impact:** keyboard user opens dropdown → expects to be IN it → arrow keys land where they expect IF rAF fires + focus lands. Today's test suite does not protect that path. The bug class the first review specifically flagged (focus contract gap is invisible to axe) is exactly what the burndown's test still doesn't catch.

### P2.1.regression — The "footnote NOT inside listbox" test is structurally vacuous; it asserts on the wrong listbox instance

**File:** `web/src/components/ModelSwitcher.test.tsx:476-491`.

The test renders TWO `<ModelSwitcher>` instances:

```
const { container } = render(<ModelSwitcher sessionId="s1" />);       // :477 (initial reset: anthropicApiKeyConfigured=null → no footnote)
resetStore({ anthropicApiKeyConfigured: false });
render(<ModelSwitcher sessionId="s1" />);                              // :479 (now configured: footnote will render)
fireEvent.click(screen.getAllByLabelText("Switch model")[0]!);         // :480 opens FIRST switcher
const listbox = screen.getByRole("listbox");                           // :481 finds the only listbox (the first one)
// ...
expect(listbox.querySelector('a[href="#/settings"]')).toBeNull();      // :487-489
```

The first instance was rendered with `anthropicApiKeyConfigured: null` and never re-renders, so its `showNoKeyHint` is false and it has NO footnote at all, regardless of whether the burndown moved the footnote outside the listbox. The query `listbox.querySelector('a[href="#/settings"]')` on the first switcher's listbox returns null whether or not the fix is in place — the test passes vacuously.

The global `screen.getByRole("link", { name: /Add an API key.../ })` lookup at `:484` does find the footnote, but it comes from the SECOND switcher whose dropdown is closed (`open` defaults to false; the click at `:480` only opened the first). Wait — actually, the second switcher's dropdown is closed too, so its footnote shouldn't render either (the footnote is rendered inside `{open && ...}`). Re-examining: the link assertion `screen.getByRole("link", ...)` should throw "not found" since neither dropdown is open with footnote visible.

If this test passes in CI, it's because of test framework quirks (the second `render` may not be cleaning up, or `screen` is querying a stale prior render). Either way, **the test does not exercise the contract it claims**. To actually pin "footnote is NOT a descendant of listbox":

```
resetStore({ anthropicApiKeyConfigured: false });    // single reset before render
render(<ModelSwitcher sessionId="s1" />);
fireEvent.click(screen.getByLabelText("Switch model"));
const listbox = screen.getByRole("listbox");
const link = screen.getByRole("link", { name: /Add an API key/ });
expect(listbox.contains(link)).toBe(false);
```

**User impact:** the structural a11y guarantee (no phantom option inside listbox iteration) is unprotected. A future refactor that moves the footnote back inside would not trip this test.

### P2.5 (re-flag, now verified against token values) — `focus:ring-cc-primary/40` fails 3:1 contrast in dark mode

**File:** `web/src/components/ModelSwitcher.tsx:270` (`focus:ring-1 focus:ring-cc-primary/40`).
**Token values (verified from `web/src/index.css`):**
- `--color-cc-primary: #d97757` (both modes, `:24` and `:193`)
- `--color-cc-bg: #262624` (dark, `:190`) / `#faf9f6` (light, `:21`)

Tailwind `ring-cc-primary/40` composites `#d97757` at 40% over `#262624` → effective ≈ `#5a3e34`. Contrast vs `#262624` ≈ 1.5:1 — **fails** WCAG 2.4.11 (Focus Appearance, 2.2 AA) 3:1 floor. In light mode the composite ≈ `#eccab0` over `#faf9f6` ≈ 1.2:1 — also fails.

The global `:focus-visible` at `index.css:349` (`outline: 2px solid var(--color-cc-primary)` — full opacity, ~3.6:1 in dark, ~2.4:1 in light) is the floor that the listbox's `focus:outline-none` deliberately suppresses. The override dilutes the floor below WCAG.

**Fixes (any one):**
1. Drop the override entirely — let the global `:focus-visible` outline apply.
2. Use `focus-visible:ring-2 focus-visible:ring-cc-primary` (full opacity, 2px wide, only on keyboard focus).
3. If the team prefers the soft visual: pair with `focus:ring-offset-2 focus:ring-offset-cc-bg` to gain the offset gap that lifts perceived contrast.

**User impact:** sighted keyboard user opens dropdown, Tab into listbox, cannot perceive the focus state — loses orientation between trigger and listbox.

## P3 — Consider

### P3.1.new — Click-outside focus-restore gate is correct for the documented case but races browser-default `mousedown`→`focus` on the click target

**File:** `web/src/components/ModelSwitcher.tsx:134-139`.

The gate reads `document.activeElement` synchronously inside the `mousedown` listener. Browser default: `mousedown` runs BEFORE the click target receives focus (focus typically lands on `mouseup` for buttons/inputs). So when focus is in the listbox and the user pointer-mousedowns on an `<input>` outside, the gate reads `focusWasInsideListbox=true` and rAF-pulls focus to the trigger — yanking from the about-to-be-focused click target.

The new test at `:425-444` doesn't catch this because it `elsewhere.focus()` BEFORE `fireEvent.mouseDown(elsewhere)`, sequencing focus first. Real users mousedown first; focus comes after. To pin the contract correctly, swap to `pointerup` / `click` for the close logic, OR set the rAF in a `setTimeout(0)` so the click-target focus has a chance to commit first and the gate reads the actual post-click activeElement.

Marking P3 because: pointer-only users don't notice (no AT cursor); keyboard-only users don't trigger this path (no mousedown); only the hybrid pointer+focus interaction loses the click-target focus. Real-world frequency low. But the first review's stated invariant ("don't yank focus from where the user just clicked") is not actually held in this edge.

### P3.4.new — Removing `models` from the open-edge effect dep array trades cursor-snap for stale-index when the list grows under an open dropdown

**File:** `web/src/components/ModelSwitcher.tsx:182` + comment block `:159-165`.

Burndown comment acknowledges the trade: removing `models` from deps prevents the cursor reset on every dynamic-list refresh while open. Correct. But if the list arrives AFTER `open` flipped true (e.g., user opened the dropdown with the static fallback while `loadBackendModels` was still in flight), the activeIndex was set from `models.findIndex((m) => m.value === currentModel)` against the OLD `models` array. When the new dynamic list arrives, the index now points at a different model. The keyDown handler's `Math.min/Math.max` clamps to bounds but doesn't re-anchor on the selected model.

User impact: visual "active highlight" silently shifts to the wrong row mid-open. Edge case (open within the inflight window), but possible. Cheap fix: gate the effect on `open && wasOpenRef.current === false && models.length > 0` to re-fire if `models` arrives after open AND the old `wasOpenRef` was an empty-list edge.

### P3.5.new — Footnote `<a>` lacks an explicit link affordance beyond color (WCAG 1.4.1 Use of Color)

**File:** `web/src/components/ModelSwitcher.tsx:328-334`.

The footnote `<a href="#/settings">` carries `block px-3 py-2 border-t border-cc-separator text-[11px] text-cc-muted hover:text-cc-fg hover:bg-cc-hover`. No `underline` class; no visual styling that says "link" until hover. The text "Add an API key in Settings to see more models." reads as plain copy; the `<a>` role is correct for AT (`getByRole("link")` succeeds), but a sighted user without hover (touch device, focused but not hovering) has no indication this is clickable.

**Fix:** add `underline underline-offset-2` or at least `text-cc-primary hover:underline` so the affordance is visible without hover.

**User impact:** sighted user reads the footnote as static help text; doesn't realize it's the one-click path to Settings. The whole point of P2 #12 (Friedman R3) is discoverability — a discoverable-only-on-hover link half-defeats it.
