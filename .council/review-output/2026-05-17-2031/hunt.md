# Hunt — Security Review

## Finding 1: Architecture reference cites `EC-13` but the canonical `conventions.md` skips from EC-12 to EC-14
- **File:** docs/reference/council-mode-architecture.mdx:125 (also referenced at lines 116, 148 framing "EC- conventions ratified in conventions.md")
- **Severity:** P1
- **Principle:** §A attack surface discipline — surface that "should not be reachable" but technically is reached; documented contracts that drift from their canonical source decay into security-through-obscurity. Hunt's discipline insists on inventory truth at the point where the contract is invoked, not in a separate doc that nobody re-checks.
- **Finding:** The page locks its security-property prose against convention IDs (good) and explicitly directs readers to `conventions.md` as the "canonical reference; this page deliberately does not restate it" (line 127). It then bullets `EC-13` as the Observer failsafe (line 125). But `conventions.md` enumerates `EC-1..EC-12`, then jumps to `AP-4` and `EC-14..EC-24`, then `EC-30..EC-33` — `EC-13` is absent. A reader following the explicit invitation to the canonical source finds the security-property bullet unbacked.
- **Consequence:** A security claim sourced to a missing convention ID is unauditable: the next person investigating "is the observer failsafe actually a ratified invariant or just doc prose?" hits a dead-end at the cited authority, and trust in the rest of the EC- citations on this page (EC-1, EC-2, EC-7, EC-8) leaks proportionally. This is exactly the audit-trail rot Hunt's §C `breach forensics` principle warns about — a forensic question with no answer at the cited authority.
- **Fix:** Either add `EC-13: Observer failsafe — recurring 5-minute tick scans `.council/checkpoints/`...` to `conventions.md` (closing the EC-12 → EC-14 gap that the reference already cites), or remove the `EC-13` citation from line 125 and re-anchor the failsafe paragraph to the project CLAUDE.md (which does define EC-13 in its convention floor). The two-source-of-truth split is the root cause; pick one and link the other to it.

## Finding 2: Architecture reference describes the write boundary as "enforced at spawn time, not at runtime" and then immediately enumerates a runtime check
- **File:** docs/reference/council-mode-architecture.mdx:140-148
- **Severity:** P2
- **Principle:** §A attack surface discipline — security-property prose must survive precise reading without contradicting itself; defence-in-depth claims that paper over their own depth invite the same "we thought the gate caught it" failure mode the depth exists to prevent.
- **Finding:** Line 142 frames the observer write boundary as "enforced at spawn time, not at runtime" — then bullets three pieces, the third of which (`observer-write-policy.ts`'s `assertObserverWriteAllowed(path, root)`) is explicitly described as resolving `realpath` and bounds-checking against the workspace root **before any write the observer might attempt** — i.e., a runtime check. The prose contradicts the bullet list it introduces.
- **Consequence:** A security reviewer comparing the doc to the code now has to decide which to trust; an operator triaging "the observer wrote outside its scope" cannot tell from the doc whether the runtime check is load-bearing (it is, per CLAUDE.md's three-piece description) or vestigial (the prose framing suggests it shouldn't exist). Defence-in-depth that is documented as defence-in-shallow is the worst of both worlds.
- **Fix:** Replace "enforced at spawn time, not at runtime" with "enforced at two layers: spawn-time argv injection (primary) and a runtime path-resolving guard (defence-in-depth)". The three-piece enumeration that follows is correct; only the topline framing needs to match it.

## Finding 3: Architecture reference frames the group-id as a "second factor" — overclaims against the actual control
- **File:** docs/reference/council-mode-architecture.mdx:173-176 (Authorization section)
- **Severity:** P2
- **Principle:** §A attack surface discipline — "secure defaults" and the corollary that security claims must name the *actual* control rather than a more-impressive-sounding adjacent control. "Second factor" has a specific meaning (a distinct authentication factor, typically possession + knowledge); using it for a per-resource authorization scope inflates the claim and creates disclosure-narrative liability if a breach later turns on what "second factor" was understood to mean.
- **Finding:** The doc says "the group id is a second factor that prevents one browser tab in a multi-user environment from accidentally targeting another tab's group." The cryptographic group-id pattern (per CLAUDE.md and `group-authorization.ts`) is a per-resource authorization scope bound to the council group — not a second authentication factor. Calling it "2FA-adjacent" language overstates its security posture; its real (and adequate) job is to bound which authenticated requests can touch which group.
- **Consequence:** If a breach disclosure later has to characterise the access controls in operator-facing language, "second factor" becomes an inaccuracy the team has to retract — exactly the multi-update, multi-correction pattern Hunt's §C `disclosure discipline` warns destroys public trust. The control is fine; the framing has more authority than the control supports.
- **Fix:** Rephrase to "a per-group authorization scope cryptographically bound to the group id, required on every council-scoped REST endpoint. It bounds blast radius: a leaked group id from one pair does not grant access to another, even though both authenticate against the same Companion token." Names what the control does, names what it protects against (enumeration / cross-group access), avoids the 2FA terminology entirely.

## Finding 4: `landing/` is not in `branding.config.json` `protectedPaths`, so the MIT-attribution URL surface is one rule edit from silent corruption
- **File:** branding.config.json:10-79 (protectedPaths block) — risk surface lives in landing/src/components/Footer.tsx:5-12
- **Severity:** P2
- **Principle:** §A attack surface discipline — "secure defaults" applied to rewriter scope. The rewriter is a controlled-rewrite tool; the safe default for surfaces that bear legally-significant text (MIT attribution + URL integrity) is to be **explicitly protected**, not to escape current rules by accident of substring shape.
- **Finding:** The Footer.tsx MIT attribution preserves `https://github.com/The-Vibe-Company/companion` and `https://thevibecompany.co` verbatim today only because the active replacement rules (`"from": "Vibe-Companion"`, `"from": "the-companion"`) happen not to substring-match `The-Vibe-Company/companion`. A future contributor widening the rule (e.g. adding `"from": "Vibe-Company"` to clean up a leftover, or making the `the-companion` rule case-insensitive) would silently rewrite the attribution URL and break the MIT-license obligation without any visible diff signal in this file's protection list. `docs/**` is protected; `landing/**` is not.
- **Consequence:** MIT attribution is a contractual obligation, not a styling choice; corrupting the URL to upstream-author identity is a license violation that compounds reputationally beyond the immediate bug. The class of failure is identical to the "Vibe-Companion → Aura Companion" pattern that *would* be applied to the wrong substring — the protection here should be belt-and-suspenders on the attribution surface specifically.
- **Fix:** Add `"landing/src/components/Footer.tsx"` to `protectedPaths` (or `landing/**` if the broader scope is acceptable). Pair with a one-line CI canary that asserts the upstream URL `The-Vibe-Company/companion` is still substring-present in Footer.tsx; a corrupted attribution then fails CI rather than ships.

## Finding 5: Guide's "Write to your workspace" cannot-clause is incomplete vs the actual three-piece boundary
- **File:** docs/guides/council-mode.mdx:26 (the "Cannot:" enumeration)
- **Severity:** P3
- **Principle:** §A attack surface discipline — secure-defaults pedagogy. The user-facing summary should not understate the defence; under-claiming creates the impression that a "near miss" is closer than it is and erodes operator confidence in the gate when they observe its three layers in logs.
- **Finding:** The guide says the observer "Cannot: Write to your workspace. The write boundary is enforced at spawn argv (tool allow-list + permission mode)." Per CLAUDE.md the boundary is three pieces — spawn-time argv injection, the allow/deny-list module with a disjointness canary at module load, **and** `assertObserverWriteAllowed`'s runtime realpath + bounds-check. The single-sentence summary mentions only the first piece. This is not marketing-overclaim (the right direction for §A) but it leaves the runtime guard invisible to the user.
- **Consequence:** A user reading only the guide who sees an `observer-write-policy.ts` log line during debug will not have framework to recognise it as a deliberate second layer; the audit narrative for "did the gate fire?" is harder to reconstruct from the user's vantage. Minor — but Hunt's discipline asks that defence-in-depth be visible at every layer of the docs, not collapsed to one.
- **Fix:** Expand to "Cannot: Write to your workspace. The write boundary is enforced in two layers — observer-specific tool allow-list and permission mode applied at spawn argv (primary), plus a runtime workspace-bounds check that resolves realpath before any attempted write (defence-in-depth)." Twelve extra words; the user now knows both gates exist.
