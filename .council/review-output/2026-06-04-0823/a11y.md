## P1 — Fix Now

### P1.1 — Listbox focus does NOT return to trigger on click-outside dismissal
**File:** `web/src/components/ModelSwitcher.tsx:107-116`
**WCAG:** 2.4.3 Focus Order; APG dialog/listbox dismissal contract.

The Escape handler at `:170-174` does restore focus to the trigger (`triggerRef.current?.focus()`), but the **click-outside** path (`:107-116`) calls only `setOpen(false)` with no focus restoration. A keyboard user who has focused the listbox via Tab and then accidentally clicks outside loses focus to `<body>`. More importantly: an assistive-tech user who triggered "click outside" via screen-reader cursor or rotor navigation also loses position.

The pattern is asymmetric — Escape restores, click-outside doesn't. Both close the same overlay; both should restore focus to the trigger when the listbox owned focus at dismissal time. Mirror what `CouncilToggle.tsx:189,211` already does (`requestAnimationFrame(() => triggerRef.current?.focus())`) but gate it on `document.activeElement` being inside `listboxRef.current` so click-outside-with-pointer doesn't yank focus from where the user just clicked.

**User impact:** keyboard / SR user loses orientation point. Next Tab lands at document start, not where they were working in the bottom bar.

### P1.2 — `tabIndex={0}` listbox + `queueMicrotask` autofocus is non-deterministic under StrictMode + JSDOM
**File:** `web/src/components/ModelSwitcher.tsx:123-132`

The open effect schedules focus via `queueMicrotask(() => listboxRef.current?.focus())`. Two concerns:

1. **React 19 StrictMode double-invokes effects in dev.** The first invocation queues a microtask; cleanup runs before the second invocation; the microtask still fires against a now-unmounted ref (`listboxRef.current` is null) and is silently swallowed. Production behaviour is fine; dev experience is a swallowed focus on every open while StrictMode is active. `CouncilToggle.tsx` uses `requestAnimationFrame` instead — switch to rAF for consistency with the rest of the codebase and to align with paint-tick (focus before paint can race with browser focus-on-mount).
2. **No test asserts focus actually lands on the listbox after open.** The test at `:122-133` clicks Escape on `screen.getByRole("listbox")` and asserts the dropdown closes — but `fireEvent.keyDown(listbox, ...)` dispatches against the element regardless of where focus is. There's no `expect(listbox).toHaveFocus()` after the open click. The producer-side test for "focus actually landed" is absent — a regression that breaks the focus call would be invisible to the suite.

**User impact:** keyboard user opens dropdown → expects to be IN it → arrow keys do nothing because focus is still on the trigger or somewhere else. The visual state ("open") and interaction state ("which element receives keystrokes") drift apart. Add a behavioural assertion: `await waitFor(() => expect(listbox).toHaveFocus())`.

### P1.3 — Space activation key scrolls page when listbox has tabIndex but is not focused
**File:** `web/src/components/ModelSwitcher.tsx:165-169`

The handler at `:166` catches `case " ":` and calls `e.preventDefault()`. This is correct **only when the event reaches the listbox handler**. If P1.2 fires (focus didn't actually land on the listbox), then a `Space` keypress while the user thinks the listbox is focused actually targets `<body>` → browser default Space = scroll-down → page jumps while the dropdown stays unchanged. The user perceives this as "dropdown doesn't accept Space" + "site randomly scrolled."

This is interlocked with P1.2 — once focus is deterministically on the listbox, Space is captured and prevented. But the test suite does NOT cover the negative case: no test asserts that pressing Space WITHOUT first focusing the listbox does NOT scroll the page. Hard to test in JSDOM (no real scrolling), but a `fireEvent.keyDown(document.body, { key: " " })` followed by `expect(document.body.scrollTop).toBe(0)` is at least an attempted canary.

Marking P1 because the underlying issue (focus landing) is the same root as P1.2; once focus is bulletproof, Space is fine.

## P2 — Fix Soon

### P2.1 — No-key footnote (`showNoKeyHint`) lives inside the `role="listbox"` container — screen-reader iterates it as if it were an option
**File:** `web/src/components/ModelSwitcher.tsx:263-267`

The "Add an API key in Settings to see more models." `<div>` is a direct child of the `role="listbox"` container (`:208`). ARIA's listbox role expects its descendants to be `option` / `group` only. A bare `<div>` child without role is non-semantic — but screen-readers in browse mode (NVDA, JAWS) and especially the macOS VoiceOver rotor will surface it as a generic group child inside the listbox, immediately after the last option. The user will hear "Add an API key in Settings to see more models" with no role announcement, and arrow-key navigation may or may not skip it depending on the SR.

The test at `:241-246` asserts only that the text is NOT in the document when a dynamic list is present, and `:251-275` asserts presence/absence based on key status. Neither verifies the SR semantics.

**Fixes:** (a) move the footnote OUTSIDE the `role="listbox"` div but inside the dropdown wrapper, OR (b) wrap it in `role="presentation"` + `aria-hidden="false"` and ensure arrow-key handler bounds (`models.length - 1`) cannot land active-descendant on it. Option (a) is structurally cleaner. Mirror via `screen.getByRole("listbox")` → `expect(within(listbox).queryByText(/Add an API key/)).toBeNull()` once moved out.

**User impact:** SR user perceives a "phantom 5th option" with no role; arrow keys appear to skip mid-list; the announcement is uncontextualized.

### P2.2 — Chevron `<svg>` on trigger has no `aria-hidden="true"`
**File:** `web/src/components/ModelSwitcher.tsx:202-204`

The dropdown indicator SVG on the trigger button:
```
<svg viewBox="0 0 12 12" fill="currentColor" className="w-2.5 h-2.5 opacity-50">
  <path d="M6 8L1.5 3.5h9L6 8z" />
</svg>
```
This decorative graphic is rendered inside the `<button>` alongside the text label and icon. Without `aria-hidden="true"`, AT may announce "image" or "graphic" between the model label and the implicit "button" announcement. Different SRs behave differently — VoiceOver tends to ignore inline `<svg>` without `<title>`; NVDA browse-mode sometimes announces "graphic." The selected-checkmark SVG at `:251-253` inside the option also lacks `aria-hidden`, but `role="option"` + the visible "selected" text + `aria-selected="true"` give context — minor.

**Fix:** add `aria-hidden="true"` (and `focusable="false"` for legacy IE11/Edge — harmless modern). The "Latest" badge `<span>` at `:245-249` IS conveyed visually — see P2.3.

**User impact:** noisy announcement of "graphic, Switch model button" instead of "Switch model button."

### P2.3 — "Latest" badge announced inline as part of the option name — verify intent
**File:** `web/src/components/ModelSwitcher.tsx:245-249`

The "Latest" badge span has no role and no `aria-hidden`. It's the only readable text in that span. SR computes the option's accessible name from concatenated text content → option announces as "Opus 4.8 Latest." This is probably FINE (the user benefits from knowing which is newest), but:

1. The test at `:222-230` asserts visual presence of "Latest" text, not the accessible-name assembly. Add `expect(screen.getByRole("option", { name: /Opus 4\.8.*Latest/ })).toBeInTheDocument()` so a future refactor that hides the badge from AT (e.g. adds `aria-hidden`) trips the test.
2. Friedman R1's intent (per PLAN.md:191) is "user with sticky 4-7 sees 4-8 Latest and decides for themselves" — explicitly intended to reach the user, including SR users. So absence of `aria-hidden` is correct here. Pin it with a behavioural test.

**User impact:** the SR-vs-sighted parity is correct but unguarded. P2 to add the regression canary, not to change behaviour.

### P2.4 — Trigger `title={...}` is not a reliable accessible-name fallback
**File:** `web/src/components/ModelSwitcher.tsx:195,201,228`

Three uses of `title=`:
- Trigger button: `title={\`Current model: ${currentOption.label}\`}` — fine, `aria-label="Switch model"` is the accessible name.
- Option div: `title={model.label}` — the truncated label uses `title` as the hover-tooltip fallback.

Per a11y reference Principle 5 and PLAN's a11y R2: when a label is truncated visually, the FULL text should remain the accessible name. The option's `name` comes from its `<span>` text content, which is the truncated rendered text after `truncate` class clips it. **Browser DOM `textContent` still returns the FULL string** (the `truncate` class only adds visual ellipsis via CSS `text-overflow`), so the accessible name IS the full label — verified by the test at `:369-382`.

But the PROMPT specifically noted: "title attribute isn't reliably announced by screen readers; consider aria-label as backup." That's true generally. Here it's a non-issue because `textContent` provides the full string. **Worth confirming**: WebKit-based screen readers (VoiceOver / Safari) sometimes use the rendered visual text instead of `textContent` for truncated nodes — this is a known WebKit divergence. If the team wants belt-and-suspenders, add `aria-label={model.label}` to the option `<div>`. Today's coverage is acceptable but fragile.

**User impact:** mostly theoretical — modern AT compute name from `textContent`. Note as P2 watchpoint, not a blocker. The existing test `:369-382` only checks `title` presence, not accessible-name. Strengthen by also asserting `expect(option).toHaveAccessibleName(long[0].label)`.

### P2.5 — Listbox `focus:outline-none focus:ring-1 focus:ring-cc-primary/40` may fail 3:1 ring contrast
**File:** `web/src/components/ModelSwitcher.tsx:213`

The listbox replaces the global `:focus-visible` outline (2px solid `cc-primary` per `index.css:349`) with a Tailwind `focus:ring-1` at 40% opacity of `cc-primary`. Two issues:

1. **`focus:` not `focus-visible:`** — fires on mouse focus too, which is mild visual noise (acceptable) and not a WCAG violation.
2. **`cc-primary/40` (40% opacity)** — likely fails WCAG 2.4.11 (Focus Appearance, 2.2 AA) 3:1 contrast against `bg-cc-bg`. The global outline is fully opaque; this override dilutes it. Sighted keyboard users may not see the focus ring against a similar-toned background.

Verify with the project's actual `cc-primary` and `cc-bg` token values. If `cc-primary` is a high-saturation color and `cc-bg` is dark/light enough, 40% may still pass. Otherwise: drop to `focus-visible:ring-2 focus-visible:ring-cc-primary` (no opacity), or remove the override entirely and let the global `:focus-visible` outline apply.

**User impact:** sighted keyboard user opens dropdown, Tab into it, can't tell visually that it has focus → loses position vs trigger button.

### P3.2 — `onClick` on `role="option"` divs is APG-conformant single-select, but no test asserts mouse-click does NOT also fire Enter via keyboard handler
**File:** `web/src/components/ModelSwitcher.tsx:227,236`

The intentional design split: keyboard activation lives on listbox `onKeyDown`; mouse/click activation lives on each option's `onClick`. This is APG-correct. No bug. Add a test that asserts click+keyboard are independent paths (click an option without keyDown reaching listbox; verify `mockSendToSession` called exactly once — already covered by `:91-100`, but worth a `keyDown(listbox, Enter)` + `click(option)` interleave test to confirm no double-dispatch).

### P3.3 — `aria-controls` on trigger not wired
**File:** `web/src/components/ModelSwitcher.tsx:187-205`

`CouncilToggle.tsx:315` pairs `aria-haspopup="listbox"` with `aria-controls="council-pairing-listbox"`. ModelSwitcher's trigger has `aria-haspopup="listbox"` but no `aria-controls={\`${idPrefix}-listbox\`}` pointing at the listbox `id`. The listbox also has no `id` (only its options do). APG dialog/combobox pattern wants the controls relationship explicit so AT can navigate trigger → owned widget. Add `id={\`${idPrefix}-listbox\`}` on the listbox div and `aria-controls={\`${idPrefix}-listbox\`}` on the trigger button.

**User impact:** SR user with rotor/element navigation can't jump directly from trigger to listbox via "go to controlled element." Minor — keyboard Tab still works.

### P3.4 — `prefers-reduced-motion` not directly tested at the component level
The global rule in `index.css:355-360` covers transitions on all elements. ModelSwitcher uses `transition-colors` on trigger and options (`:190, :229`). Reduced-motion is handled globally — no component-level work needed. Note for thoroughness only.
