# Spec: Авторизация LLM — фаза 1: правда о статусе и понятные ошибки

**Date:** 2026-11-13
**Tier:** Feature · **Status:** Confirmed scope (phase 1 of `specs/llm-auth-resilience-v1.md`)
**Authorship:** AI-generated; owner approval covers scope, not a code review.
**Covers parent stories:** A.2 (статус + диагностика), C.2 (ошибка с причиной и действием).

## Objective

Владелец должен за секунды понимать, что случилось с авторизацией Claude и Codex, не заходя на сервер. Фаза 1 даёт единый статус провайдера, диагностику `doctor` и честные ошибки в сессии. Вход и перелогин из UI — фаза 2. Здесь достаточно показать действие: что сделать и где.

## Context

Сейчас есть только локальная проверка «файл учётных данных присутствует / истёк по сроку» для бейджа на экране новой сессии. Плюс панель лимитов, которая при любом сбое молча исчезает. Реальные инциденты, на которых проверяется фаза:

- Токен Claude мёртв вместе с refresh-токеном. Бейдж «authorized», панель лимитов пуста, автоназвание падает 400.
- Сервис запускает старый `claude` (PATH или не переключённый симлинк). Ошибка «version X required» выглядит как проблема модели.
- Копия ротируемых учётных данных в другом HOME или у другого системного пользователя инвалидировала основной вход.
- У Codex каждая сессия хранит свою копию учётных данных: после перелогина старая сессия остаётся на мёртвом токене.
- «Codex protocol drift» скрывал `unauthorized`.
- «Out of extra usage» при 3% пятичасового окна: модель вне тарифа.
- Баннер «session limit» остался после сброса окна и блокировал ввод.

## Scope

### In scope
- Статус провайдера в UI и в CLI `aura-companion` с проверкой у провайдера, а не только по файлу.
- Диагностика `doctor` в CLI и тот же отчёт в UI.
- Классификация ошибок хода: авторизация / лимит (с указанием окна) / extra usage / нет связи / устаревший CLI.
- Панели, зависящие от авторизации (лимиты), показывают причину вместо молчаливого исчезновения.

### Out of scope
- Вход и перелогин из UI (фаза 2), мастер установки (фаза 3), предупреждения заранее, запасной способ входа и маркировка моделей (фаза 4).
- Автоматическое исправление найденных проблем: фаза 1 только сообщает и подсказывает.

### Non-goals
- Частый опрос провайдера в фоне ради «живого» статуса.

## Stories

### Story 1: статус провайдера

**When** сессии ведут себя странно, **I want to** открыть статус Claude и Codex, **so I can** сразу понять, виновата ли авторизация.

Given авторизованный провайдер с рабочими учётными данными
When владелец открывает статус в UI или выполняет команду статуса в CLI
Then видны: состояние «работает», аккаунт, тариф, способ входа (подписка или API-ключ), срок действия токена и время последней успешной проверки

Given учётные данные присутствуют, но провайдер их отклоняет (истёк refresh, отозваны)
When статус обновляется
Then состояние «недействительны», а не «авторизован», и указано действие: перелогиниться (со ссылкой на текущую инструкцию до появления фазы 2)

Given провайдер не отвечает по сети
When статус обновляется
Then состояние «нет связи», показано время последней успешной проверки, и провайдер не помечен как истёкший

Given проверка у провайдера не может выполниться без расхода токенов модели
When статус обновляется
Then показан локальный статус с пометкой «не проверено у провайдера», и токены модели не тратятся

Given статус открыт в UI и в CLI одновременно
When оба показывают один провайдер
Then состояние, аккаунт и тариф совпадают

### Story 2: диагностика `doctor`

**When** что-то не работает и непонятно почему, **I want to** запустить одну проверку, **so I can** получить список конкретных проблем с действиями.

Given сервис запускает бинарь CLI с другим путём или версией, чем установлен у пользователя сервиса
When владелец запускает диагностику
Then показаны оба пути и обе версии и действие по исправлению

Given версия CLI, которой реально запускаются сессии, ниже требуемой для выбранной модели
When владелец запускает диагностику
Then проблема названа «устаревший CLI» с требуемой версией, а не «нет доступа к модели»

Given на хосте есть независимая копия ротируемых учётных данных (другой HOME, другой системный пользователь, сэндбокс, копия в сессии)
When владелец запускает диагностику
Then показано предупреждение с местом копии и риском, а содержимое копии не выводится

Given учётные данные принадлежат не пользователю сервиса или недоступны ему для чтения
When владелец запускает диагностику
Then проблема названа с владельцем файла и пользователем сервиса

Given проблем нет
When владелец запускает диагностику
Then отчёт по каждому провайдеру «всё в порядке», код возврата CLI — успех; при найденных проблемах код возврата ненулевой

### Story 3: честная ошибка в сессии

**When** ход падает из-за провайдера, **I want to** видеть настоящую причину и одно действие, **so I can** не расследовать журналы.

Given провайдер отклонил авторизацию, в том числе нестандартным кадром, который раньше показывался как «protocol drift»
When ошибка показывается в сессии
Then она названа ошибкой авторизации с указанием провайдера и действием «перелогиниться»

Given исчерпано окно подписки (5h или 7d)
When ошибка показывается
Then указано, какое окно, и время его сброса

Given ход ушёл в extra usage, а кошелёк extra usage пуст или отключён
When ошибка показывается
Then указано, что исчерпан именно extra usage, а не окно подписки; если выбранная модель вне тарифа, это названо как вероятная причина

Given окно лимита, на которое ссылается баннер, уже сброшено
When владелец открывает сессию или отправляет сообщение
Then баннер не показывается, и сообщение уходит в CLI

Given провайдер недоступен по сети
When ход падает
Then показано «нет связи с провайдером» с повтором одним действием, и это не названо ошибкой авторизации

Given сессия Codex работает на старой копии учётных данных, а основной вход уже обновлён
When ход падает на авторизации
Then ошибка сообщает, что сессия использует устаревшие учётные данные, и предлагает перезапустить сессию

### Story 4: панели не исчезают молча

**When** данные о лимитах недоступны, **I want to** видеть почему, **so I can** не принимать пустую панель за «всё хорошо».

Given запрос лимитов провалился из-за авторизации
When открыта панель лимитов
Then вместо пустоты показано «нет данных: авторизация Claude недействительна» со ссылкой на статус

Given лимиты недоступны, потому что вход идёт по API-ключу (у ключа нет окон подписки)
When открыта панель лимитов
Then показано, что окна подписки не применяются к входу по API-ключу

## Boundaries

### ✅ Always
- Одинаковое поведение для Claude и Codex; если провайдер не отдаёт какое-то поле (например тариф), показывается «неизвестно», а не пусто.
- Токены, ключи и содержимое учётных данных никогда не попадают в UI, логи, вывод CLI и записи протокола. Можно показывать только пути, владельцев, сроки и хэш-префиксы.
- Регрессионный тест на каждый инцидент из Context (воспроизведение кадров из записей, где есть).
- Тексты ошибок и статусов одинаковы в UI и CLI.

### ⚠️ Ask first
- Любой новый сетевой запрос к провайдеру, частота проверок и их стоимость.
- Изменения в том, как сессии получают учётные данные при запуске (это фаза 2).

### 🚫 Never
- Обновлять (refresh) учётные данные из процесса диагностики или статуса так, чтобы ротация могла инвалидировать вход сессий.
- Читать, копировать или выводить содержимое найденных копий учётных данных.
- Менять PATH сервиса, симлинки CLI или systemd-юнит в рамках `doctor`: только сообщать.

## Success Metrics

- Каждый из 7 инцидентов Context распознаётся статусом, `doctor` или ошибкой сессии с правильной причиной в тестах.
- Ноль случаев «бейдж авторизован, а провайдер отклоняет» после выкатки.

## Assumptions

- Аккаунт и тариф можно получить у провайдера без расхода токенов модели (unconfirmed — проверить для Claude и Codex; иначе работает AC «не проверено у провайдера»).
- Ссылки на текущие ручные инструкции перелогина допустимы как временное действие до фазы 2 (unconfirmed).
