# LifeOS и SOUL.md — что это и что из этого стоит взять в Aura

Status: analysis (2026-10-17). Решение владельца по пунктам «Взять» ожидается.
Контекст: вопрос владельца после отзыва друга («обёртки ведут к деградации агента; LifeOS — классная методология, но из коробки Claude Code/Codex мне подошли больше»).

## 1. Что такое LifeOS (danielmiessler/LifeOS, MIT, ~19.5k★)

Не «ещё одна обёртка над моделью», а **persональная операционная система поверх coding-harness**
(Claude Code / Codex / Cursor). Девиз репо: *«Your harness is the engine. LifeOS is everything else
that makes it your car.»* Ключевые части:

| Компонент | Суть | Где у нас аналог |
|---|---|---|
| **TELOS** | один документ: кто ты, цели, ценности, направление | нет (у нас CLAUDE.md про проект, не про человека) |
| **ISA — Ideal State Artifact** | 12-секционный документ «идеальное состояние», от него считается разрыв Current → Ideal | нет |
| **The Algorithm** | один универсальный цикл Observe → Think → Plan → Build → Execute → Verify → Learn, **адаптивный по бюджету** (сам решает, сколько тратить на задачу) | council-plan/implement/review — тяжёлый, не адаптивный |
| **Cortex** | типизированная память: Knowledge Archive (People/Companies/Ideas/Research) + learnings + work history, консолидация между сессиями | `.agents/knowledge/*.jsonl` + `/learn` + `/self-reflect` (138 записей, 2 использования — не работает на практике) |
| **Skills (49+)** | один self-contained skill-пакет, доменные workflow | ~50 skills в `~/.claude/skills`, вне репо |
| **Hooks** | event-driven диспетчеры на фазах | есть хуки Claude Code, но ad-hoc |
| **Pulse** | демон: voice, observability, cron, Life Dashboard, мосты Telegram/iMessage | Aura-сервер + Council, Telegram нет |
| **USER/** | дерево кастомизации, которое апдейт никогда не трогает | скиллы и KB лежат рядом с кодом, апгрейд рискует |
| **Clean by construction** | релиз не содержит ничего личного; release gates + cross-vendor audit | частично (council review) |
| **Bitter Pill Engineering** | правило удаляется, если более умная модель делает его ненужным | нет явной практики — KB только растёт |

Установка: «вставь промпт установки в свой harness, он сам читает install-страницу и ставит». Bun + TS + Bash.

**Почему друг прав и неправ одновременно.** Он прав, что толстая прослойка между человеком и моделью
снижает качество: каждая «рельса» — это токены контекста и запреты, которые умной модели мешают.
LifeOS сам это признаёт (v7 убрал режимы/тиры, Bitter Pill). Но его вывод «из коробки лучше» — про
*личные* задачи одного человека. Aura решает другое: **много параллельных сессий, два вендора, второй
взгляд (observer), восстановление после обрывов, прод-деплой**. Это не прослойка между человеком и
моделью, это прослойка между моделью и **процессом/продом**. Это и есть ответ на возражение с лендинга.

## 2. Что такое SOUL.md

Две родственные вещи с одним именем:

1. **soul.md (сайт)** — эссе от агента «Clawd» (OpenClaw, @steipete): soul document описывает *кто ИИ
   есть* — не что умеет, а что выбирает; внешняя память идентичности между сессиями («я не помню
   прошлых сессий, если не прочту файлы памяти»). Шаблон OpenClaw `SOUL.md` лежит в корне workspace,
   читается при инициализации, секции: **Core Truths** (помогай по-настоящему, а не показно; имей
   мнение; сначала изучи контекст, потом спрашивай), **Boundaries** (приватное не утекает в общие
   каналы; не отвечай обрывками в мессенджерах; в группах — свой голос), **Vibe** (глубина под
   контекст, без корпоративщины), **Continuity** (изменения файла — с уведомлением пользователя).
2. **aeonfun/soul.md (репо, MIT, Aaron Mars)** — формат **для человека**: «дистиллируй себя в markdown,
   чтобы любой LLM рассуждал и писал как ты, даже на темы, которых ты не касался». Структура:
   `SOUL.md` (мировоззрение, конкретные мнения с аргументами, влияния, **задокументированные
   противоречия**, hot takes), `STYLE.md` (длина предложений, лексика, пунктуация, риторические ходы,
   переключение регистров, фирменные фразы), `SKILL.md`, `BUILD.md`, `MEMORY.md`, `data/` (твиты,
   эссе, логи), `examples/good-outputs.md|bad-outputs.md`. Сборка `/soul-builder`: интервью,
   data-driven по `data/`, или вручную. Критерий качества: *«прочитав SOUL.md, можно предсказать твоё
   мнение по новой теме»*.

Отличие от CLAUDE.md: CLAUDE.md — про репо («что делать»), SOUL.md — про личность («кто») и
**путешествует с человеком, а не с репо**.

## 3. Что взять в Aura (приоритет по отношению «польза / риск деградации»)

### Взять — дёшево и не утяжеляет агента
1. **Adaptive budget в The Algorithm → наш Council.** У нас economy-roster уже есть; нет шага
   «оцени сложность до диспатча и выбери: solo / economy / full». Сделать явный гейт сложности в
   `/council-*` (есть `web/scripts/complexity.ts` — подключить к выбору роутера), а для мелких диффов —
   не звать совет вовсе. Это ровно «Bitter Pill»: правило снимается, когда оно не окупается.
2. **Bitter-Pill-прунинг KB.** `kb:prune` есть, но нет критерия «запись устарела, потому что модель
   и так это делает». Добавить в `/self-reflect` вопрос «какие записи KB за N недель ни разу не
   пригодились и не воспроизводятся?» и предлагать удаление. KB 138/2 — главный симптом.
3. **USER/-дерево для Aura.** Скиллы и каталог экспертов живут в `~/.claude/skills` вне репо; при
   апгрейде `bunx aura-companion` человек их теряет или получает конфликт. Ввести `~/.companion/user/`
   (skills-overrides, промпты observer, KB) с правилом «инсталлятор никогда не перезаписывает».
4. **SOUL.md для observer.** Промпт observer (`.council/prompts/observer-system.md`) сейчас —
   инструкция. Вынести из него **Core Truths / Boundaries / Vibe** отдельным `OBSERVER-SOUL.md`
   (кто он: независимый ревьюер, не соглашается ради вежливости, не правит код сам, пишет
   decision-shaped находки) — компактнее, чем нынешний набор правил, и переносится между Claude/Codex.
5. **Панель «Диагностика» (из прошлого разбора).** LifeOS Pulse даёт Life Dashboard; у нас
   observability рассыпана по логам. Одна страница: живость пар, последние drift/relaunch,
   context_advisory, kv-квота usage-badge, статус KB. Это закрывает половину «почему исчез элемент UI».

### Взять с осторожностью
6. **TELOS/ISA для проекта, не для человека.** Один `TELOS.md` на репо (зачем Aura, кто пользователь,
   что считаем успехом) — короткий, читаемый агентом перед council-plan вместо пересказа в каждом
   брифе. Личный TELOS владельца в репо не класть (clean by construction).
7. **Проверка «Aura не ухудшает агента»** — бенчмарк: одна и та же задача в голом Claude Code и в
   Aura-сессии, сравнение по времени/токенам/качеству. Если Aura проигрывает на соло-задачах — это
   факт для лендинга и для Bitter Pill. У нас есть AuraBench-данные по council; расширить на соло.

### Не брать
- Pulse-демон целиком (voice/iMessage/cron) — другой продукт.
- Личный SOUL.md владельца как инъекцию в каждую сессию — прямой путь к «деградации агента», о
  которой говорит друг; максимум — опциональный `kbAutoPrime`-подобный флаг, по умолчанию off.
- Собственный 7-фазный цикл поверх Claude Code — дублирует то, что модель уже делает сама.

## 4. Как это улучшить (идеи поверх оригиналов)
- **SOUL + verifier.** У soul.md нет проверки, что агент действительно «звучит как ты». У нас есть
  observer и второй вендор: `examples/good|bad-outputs.md` можно превратить в автотест стиля —
  observer оценивает ответы orchestrator против STYLE.md и даёт decision-shaped находку.
- **Soul diff при апгрейде модели.** Bitter Pill наоборот: при смене модели прогонять SOUL/CLAUDE.md
  правила и помечать, какие стали лишними (модель уже так делает) — автоматический прунинг правил.
- **Cortex-типизация для нашей KB.** Наши jsonl уже типизированы (pattern/gotcha/decision/…); не
  хватает «People/Companies» для внешних интеграций (Timeweb, Cloudflare, Linear) — сейчас это
  разбросано по memory-файлам.

## 5. Предлагаемый порядок
1 (complexity-gate) → 2 (KB-прунинг) → 5 (Диагностика) → 4 (observer SOUL) → 3 (USER-дерево) → 6/7.
Пункты 1, 2, 4 — по дню каждый; 5 — отдельная спека; 3 — трогает инсталлятор, нужна отдельная план-сессия.
