# Spec: Aura Meta-Diet + AuraBench — «убрать всё, что не доказало marginal value»

**Date:** 2026-09-28
**Status:** Draft (исполняется автономно по `specs/aura-meta-diet/RUNBOOK.md`)
**Tier:** Product (эпик из 6 фаз; каждая фаза исполняется как отдельный PR)

## Vision

Ядро Aura Companion здоровое; вокруг него вырос «экзоскелет» мета-слоёв (правила, KB, рефлексия, self-improvement, evolve, Council, Observer, эксперты, auto-proceed, накопленная история), и ни один слой не доказал, что даёт больше пользы, чем стоит. Цель эпика — сократить управляющий контекст, свести дублирующие системы к одной, переложить протокольную работу с LLM на хост и **измерить** вклад каждого слоя против «голых» Claude Code / Codex. Why now: 194 смёрдженных PR дают достаточно реальной истории для бенчмарка, а каждый новый слой без измерения увеличивает долг. Итог — проверяемое утверждение вида «на задачах класса N Aura поднимает success rate с X% до Y% при +Z% стоимости», пригодное для лендинга auraco.space.

## Problem Statement (проверено по репо 2026-09-28)

- **Три** хранилища самообучения, а не два: `.agents/knowledge/*.jsonl` (127 записей), `.learnings/*.md` (skill `self-improvement` + UserPromptSubmit-хук, который напоминает о нём на *каждом* промпте) и авто-память Claude вне репо. Все три претендуют на «промоушен в CLAUDE.md».
- KB не проходит свой lifecycle: 124/127 записей `high`, суммарно `usageCount=2`, `helpfulCount=9`, `promoted=0`.
- `CLAUDE.md` — 33 KB / 383 строки, плотность правил (EC-*/AP-*) высокая.
- `.council/prompts/observer-system.md` — 13.9 KB; LLM отвечает за имена файлов, id группы, версии схем, sequencing — это работа хоста.
- `session-orchestrator.ts` — **4 824 строки** (в коде ещё написано «1900+» — комментарий устарел).
- 51 процессный документ (HANDOFF/PLAN/CLOSURE/BUG/…) в корне репо + 51 handoff в `.council/handoffs`, `.council/` — 15 MB на диске.
- Observer precision corpus: 5 размеченных находок (raw precision 0.50 → 0.667 после grounding, false STOP 0.333). Статистически ничего не доказывает.
- `web/evals/tasks/` — 9 регрессионных сценариев; нет ни одного сравнения «Aura vs naked agent».

## Target Users

### Мейнтейнер Aura (Антон)
- **Context:** запускает сессии и Council-пары на прод-боксе ежедневно.
- **Primary need:** меньше «бюрократии» в контексте агента без потери надёжности.
- **Success looks like:** агент реже нарушает правила и реже тратит ходы на протокол; решения о слоях принимаются по цифрам.

### Внешний пользователь auraco.space
- **Context:** выбирает, ставить ли Aura поверх своего Claude Code / Codex.
- **Primary need:** честное доказательство, что это не «ещё один wrapper».
- **Success looks like:** видит на лендинге измеренный lift с методикой и сырыми данными.

## Scope

### In scope (v1)
1. Единая система обучения: `.agents/knowledge` — единственный source of truth.
2. Жизненный цикл и health-отчёт KB.
3. CLAUDE.md ≤ 15 KB, остальное — в документы, загружаемые по необходимости.
4. Observer отвечает только суждением; весь протокольный конверт формирует и пишет хост.
5. Расширенный детерминированный grounding.
6. Архивация исторических артефактов из активного контекста.
7. Декомпозиция `session-orchestrator.ts` по capability.
8. Независимые флаги слоёв: knowledge / observer / council / auto-proceed.
9. AuraBench (≥ 30, цель 50 задач из истории PR) + ablation-прогон + отчёт Aura Lift.
10. Черновик блока лендинга с цифрами из отчёта.

### Out of scope — future
- Вынос Council Engine в отдельный npm-пакет (только архитектурная граница сейчас).
- Сбор 100–200 human-labeled Observer-находок (нужен человек; готовим только инструмент и очередь разметки).

### Non-goals
- Не удаляем крупные подсистемы (Council, Observer, grounding, state machine, recordings, redteam, provider abstraction).
- Не меняем поведение group state machine и wire-протокол браузера.
- Не оптимизируем стоимость продовых Council-прогонов (это закрыто PRO Economy #206–211).

## Stories

### A. Обучение и контекст

#### Story A1: одна система обучения
**When** агент сталкивается с ошибкой, коррекцией или находкой, **I want to** чтобы она попадала в одно хранилище, **so I can** не иметь конкурирующих истин.

Given существующие записи `.learnings/*.md`
When выполняется миграция
Then каждая содержательная запись либо перенесена в KB с провенансом, либо помечена как дубликат/мусор в отчёте миграции; ни одна не потеряна молча

Given миграция завершена
When ищется skill `self-improvement` в репо (каталог скилла, симлинки, упоминания)
Then его нет: skill удалён полностью, единственный путь фиксации знаний — `/learn`

Given репозиторий после миграции
When ищутся инструкции, предписывающие писать в `.learnings/`
Then внутри репо их ноль

Given хук вне репо, напоминающий о `.learnings/`
When исполнитель доходит до него
Then хук не изменяется, а готовый патч лежит в очереди «Ask first»

#### Story A2: KB с работающим lifecycle
**When** я открываю health-отчёт KB, **I want to** видеть реальное использование записей, **so I can** архивировать мёртвые.

Given KB
When запускается health-команда
Then выводятся total, used≥1, helpful≥1, promoted, stale, never-surfaced, распределение confidence

Given выполнение `/prime`
When запись показана агенту
Then её счётчик использования увеличивается и сохраняется на диск

Given запись, не показанная 20 сессий подряд
When запускается прунинг
Then она переносится в архив (не удаляется) с причиной

Given повреждённая строка JSONL
When запускается health-команда
Then строка репортится с номером, остальные обрабатываются, exit code ненулевой

#### Story A3: CLAUDE.md ≤ 15 KB
**When** агент стартует сессию, **I want to** получать только load-bearing правила, **so I can** тратить reasoning на задачу.

Given новый CLAUDE.md
When измеряется размер
Then ≤ 15 360 байт

Given любое правило из старого CLAUDE.md
When проверяется его судьба
Then оно либо в новом CLAUDE.md, либо в документе, на который CLAUDE.md ссылается одной строкой, либо в отчёте «удалено как устаревшее» с причиной

Given ablation AuraBench (фаза 6) показывает регресс с новым CLAUDE.md > 5 п.п. success rate
When формируется отчёт
Then регресс выделен как блокер и не маскируется

### B. Observer и Council

#### Story B1: Observer = только суждение
**When** Observer ревьюит чекпоинт, **I want to** чтобы он возвращал только список находок, **so I can** не зависеть от того, правильно ли LLM реализовал протокол.

Given Observer-промпт после рефакторинга
When измеряется размер
Then ≤ 5 KB и не содержит упоминаний имён файлов ревью, id группы, версий схем, sequencing

Given Observer вернул находки
When хост их принимает
Then хост сам добавляет все служебные поля, валидирует и атомарно пишет ревью; существующие потребители (grounding, fanout, UI, eval sidecar) работают без изменений контракта

Given Observer вернул невалидный ответ
When хост его парсит
Then ревью не пишется, фиксируется структурированный лог, группа не деградирует от одного плохого ответа

Given пары `claude+claude` и `claude+codex`
When прогоняются replay-тесты обоих провайдеров
Then оба зелёные

#### Story B2: детерминированный grounding расширен
**When** Observer выдаёт STOP, **I want to** проверять его кодом, а не промптом, **so I can** снизить false STOP.

Given STOP со ссылкой на строку, которой нет в файле
When работает grounding
Then STOP понижается до NOTE с причиной

Given STOP на строку, не изменённую в чекпоинте
When работает grounding
Then STOP понижается до NOTE с причиной

Given STOP, чей claim не упоминает ни один идентификатор с процитированных строк
When работает grounding
Then находка помечается «weak evidence», а не удаляется

Given precision corpus
When запускается precision-раннер
Then выводится false STOP rate до/после, и новый gate не ухудшает recall зафиксированного корпуса

#### Story B3: очередь human-разметки
**When** реальные находки накапливаются, **I want to** размечать их пачкой, **so I can** дойти до 100–200 меток.

Given записи находок из прод-recordings
When запускается экспорт
Then создаётся label sheet без дублей с уже размеченными

Given размеченных STOP < 100
When формируется отчёт
Then утверждение «Observer полезен» помечено как «недоказано», gate «STOP precision > 90%» — как «не оценён»

#### Story B4: экономный expert dispatch
**When** Council ревьюит изменение, **I want to** медиану ≤ 3 экспертов, **so I can** не платить за театр.

Given run-stats Council за последний месяц
When строится отчёт
Then показана медиана и распределение экспертов по размеру диффа

Given предложенная политика отбора
When её применяют к истории
Then медиана ≤ 3, а fail-closed линзы (security, fowler, willison, beck) не отбрасываются при совпадении домена

Given живые council-скиллы вне репо
When исполнитель готов их менять
Then изменения оформлены патчем в очереди «Ask first», живые файлы не тронуты

### C. Структура кода и репо

#### Story C1: оркестратор — дирижёр
**When** я читаю `session-orchestrator.ts`, **I want to** видеть делегирование capability-модулям, **so I can** менять одну capability без каскада.

Given оркестратор после рефакторинга
When измеряется размер
Then ≤ 1 800 строк, выделены минимум: Council lifecycle, Observer scheduler, Session recovery, Auto-proceed controller, Checkpoint pipeline

Given полный набор тестов до рефакторинга
When запускается после каждого шага
Then ни один существующий тест не удалён и все проходят

Given незакоммиченная правка в `session-orchestrator.ts` в прод-чекауте
When начинается фаза
Then исполнитель не трогает прод-чекаут; правка фиксируется в очереди «Ask first»

#### Story C2: история вне активного контекста
**When** агент ищет по репо, **I want to** не находить устаревшие handoff'ы, **so I can** не путать историю с текущими правилами.

Given 51 процессный документ в корне и `.council/handoffs|review-output|implementation-logs`
When выполняется архивация
Then они перенесены в `docs/history/` с сохранением git-истории; в корне остаются только README/CHANGELOG/CLAUDE/AGENTS/conventions/LICENSE/WEBSOCKET_PROTOCOL_REVERSED/SELF-LEARNING

Given код, тесты или скиллы, ссылающиеся на перемещённые пути
When выполняется поиск ссылок
Then все ссылки обновлены, тесты зелёные

#### Story C3: флаги слоёв
**When** я запускаю сессию, **I want to** независимо включать knowledge / observer / council / auto-proceed, **so I can** проводить ablation и выключать бесполезное.

Given все флаги в значении по умолчанию
When стартует сессия
Then поведение идентично текущему проду

Given флаг `knowledge=off`
When стартует сессия
Then агент не получает KB-контент и KB-инструкций

Given неизвестное значение флага
When сервер стартует
Then флаг fail-closed к значению по умолчанию и пишется предупреждение

### D. AuraBench

#### Story D1: корпус задач
**When** я хочу измерить Aura, **I want to** иметь корпус реальных задач из истории, **so I can** не мерить на синтетике.

Given смёрдженные PR
When строится корпус
Then ≥ 30 (цель 50) задач: у каждой базовый коммит, текст задачи без подсказок решения, скрытые тесты из PR, класс (bugfix/feature/refactor/architecture/security/ui/debug)

Given задача, у PR которой нет тестов, отличающих «до» от «после»
When она валидируется
Then она исключается с причиной

Given задача
When скрытые тесты запускаются на базовом коммите
Then они падают, а на merged-коммите проходят (иначе задача исключается)

#### Story D2: ablation и Aura Lift
**When** корпус готов, **I want to** прогнать варианты A–G, **so I can** получить lift по слою.

Given варианты A naked Claude, B naked Codex, C Claude+knowledge, D Claude+Observer, E Claude+full Council, F Codex+Aura, G Codex+Council
When прогон завершён
Then для каждой пары (задача, вариант) записаны: completed, hidden tests passed, regressions, wall clock, turns, tool calls, tokens in/out, cost, files touched, LOC ±

Given 5 повторов на ячейку
When строится отчёт
Then Aura Lift = (Q_aura − Q_base)/(Cost_aura/Cost_base) с доверительными интервалами по классам задач

Given исчерпан лимит подписки/API
When прогон упирается в лимит
Then прогон ждёт сброса и продолжает с того же места без дублирования завершённых ячеек

Given прогон
When агент в варианте работает
Then он изолирован от прод-сервиса, прод-сессий и прод-чекаута

#### Story D3: вывод для лендинга
**When** отчёт готов, **I want to** получить блок лендинга с цифрами, **so I can** продавать доказуемый результат.

Given отчёт Aura Lift готов и черновик ещё не одобрен человеком
When исполнитель завершает D3
Then лендинг не публикуется и не деплоится; черновик лежит только в ветке, решение о размещении принимает человек после чтения отчёта

Given отчёт Aura Lift
When генерируется черновик
Then каждая цифра на лендинге ссылается на строку отчёта, есть ссылка на методику и сырые данные

Given lift отрицательный или статистически незначим
When генерируется черновик
Then слоган не утверждает превосходство; вместо него честная формулировка «где помогает / где нет»

## Technical Context

- **Stack:** Bun + Hono + TS / React 19 + Zustand / Vitest + vitest-axe; существующая eval-инфраструктура `web/evals` — расширять её, а не строить параллельную.
- **Host:** этот бокс — прод (`aura-companion.service`, :3456). Любая работа — в отдельном клоне; бенчмарк — в отдельном инстансе с отдельным портом и state-директорией.
- **CLI:** Claude Code 2.1.283, Codex 0.142.5; лимиты подписки → прогон обязан переживать паузы.
- **Existing constraints:** convention floor AP-1..3, EC-1..13 в CLAUDE.md — не нарушать; pre-commit hook на этом боксе всегда падает (EACCES) → верификация вручную + `--no-verify`.

## Boundaries

### ✅ Always
- Работать в клоне `/home/auracomp/aura-diet/repo`, ветки от `diet/main`, одна фаза = один PR в `diet/main`.
- Перед каждым коммитом: `bun run typecheck` + таргетные тесты зоны + `test:a11y` при изменениях UI; с unset `AURA_*_TIMEOUT_MS`.
- Переносить, а не удалять (история, KB-записи, скиллы).
- Писать прогресс в `STATE.json` и `JOURNAL.md` после каждого шага.

### ⚠️ Ask first (исполнитель кладёт в `ASK-FIRST.md` и продолжает другие фазы)
- Любые изменения вне репо: `~/.claude/skills/*`, `~/.claude/settings.json`, хуки, авто-память.
- Мёрдж `diet/main` → `main`, деплой, рестарт сервиса, публикация лендинга.
- Удаление теста, изменение wire-протокола браузера или формата recordings.
- Изменение незакоммиченной правки в прод-чекауте.

### 🚫 Never
- Трогать `/root/aura-companion` (прод-чекаут), `aura-companion.service`, прод-порт 3456, `$TMPDIR/vibe-sessions` прода.
- Пушить в `main`, `git reset --hard`, `git config` (идентичность — per-command `-c`).
- Публиковать цифры лендинга, не подкреплённые отчётом.
- Удалять тесты, чтобы стало зелёным.

## Success Metrics

### Launch criteria
- Все ACs фаз 1–5 зелёные, `diet/main` проходит полный typecheck + тесты.
- CLAUDE.md ≤ 15 KB, Observer-промпт ≤ 5 KB, оркестратор ≤ 1 800 строк.
- Отчёт AuraBench: ≥ 30 задач × 7 вариантов × 5 повторов, с Aura Lift по классам.

### 30-day
- KB: доля записей used≥1 > 30%.
- Observer: ≥ 100 размеченных STOP; STOP precision измерен.

## Recommended Decomposition

Фазы 1–3 не зависят от бенчмарка; фаза 5 зависит от флагов (фаза 4); фаза 6 — от 5.

1. **Гигиена:** C2 архивация, A1 слияние обучения, A2 KB health — дёшево, снимает шум для всех следующих фаз.
2. **Контекст:** A3 CLAUDE.md, B4 отчёт dispatch + патч.
3. **Observer:** B1 host-envelope, B2 grounding, B3 очередь разметки.
4. **Код:** C1 декомпозиция оркестратора, C3 флаги слоёв.
5. **AuraBench корпус:** D1.
6. **Ablation + отчёт + лендинг:** D2, D3, повторная проверка A3 на регресс.

## Assumptions

- Лимитов подписок Claude/Codex хватит на многодневный прогон (confirmed 2026-09-28).
- CI гоняется на PR в не-`main` ветки; если нет — локальная верификация авторитетна (unconfirmed).
- Модели в вариантах фиксируются одинаковыми внутри провайдера (Claude: default CLI модель; Codex: default) (unconfirmed).
- Хранилище авто-памяти Claude остаётся отдельным (оно не про репо) — сливаются только репо-системы (unconfirmed).

## Decisions (confirmed 2026-09-28)

- 5 повторов на ячейку.
- Сырые данные бенчмарка публикуются в репо (`docs/aurabench/`) — без секретов, токенов и путей к прод-данным.
- Skill `self-improvement` удаляется полностью (не адаптер).
- Лендинг: сначала отчёт, решение о размещении — за человеком.
