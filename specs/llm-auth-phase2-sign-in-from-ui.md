# Spec: Авторизация LLM — фаза 2: вход и перелогин из UI

**Date:** 2026-11-14
**Tier:** Feature · **Status:** Confirmed scope 2026-11-14 (owner: autonomous run, recommended defaults applied)
**Authorship:** AI-generated; owner approval covers scope, not a code review.
**Covers parent stories:** B.1 (вход с headless-сервера), B.2 (не тот аккаунт/тариф), B.3 (живые сессии выздоравливают) из `specs/llm-auth-resilience-v1.md`.
**Builds on:** фаза 1 (`specs/llm-auth-phase1-status-and-errors.md`, #455–#459): статус провайдера, doctor, карточка отказа хода, причины в панели лимитов.

## Objective

Фаза 1 честно говорит «вход Claude/Codex недействителен — войдите заново», но сам вход по-прежнему требует ssh, tmux и ручной вставки кода от имени пользователя сервиса. Фаза 2 закрывает этот разрыв: владелец входит или перелогинивается из браузера (или командой `aura-companion`), сразу видит, какой аккаунт и тариф привязались, а уже открытые сессии и пары продолжают работать на новом входе.

## Context

Инциденты, на которых проверяется фаза:

- Claude OAuth умер вместе с refresh-токеном. Лечилось только интерактивным `claude` в tmux под пользователем сервиса.
- Codex-вход на сервере ждёт редирект на `localhost` сервера. Из браузера владельца работает только вход по одноразовому коду устройства, и есть ловушка: вход под другим системным пользователем или в другом HOME.
- Каждая Codex-сессия держит свою копию входа. После перелогина живые сессии остаются на мёртвом токене (фаза 1 это уже распознаёт и пишет «перезапустите сессию»).
- Браузер был залогинен в PRO вместо MAX. Вход прошёл «успешно», а ошибку заметили позже по расходам.

## Scope

### In scope
- Вход по подписке (Claude, ChatGPT/Codex) из UI и из CLI `aura-companion`. Работает на удалённом сервере и на локальной установке.
- Точки входа: карточка «LLM sign-in» на Diagnostics, действие «войти заново» в карточке отказа хода и в причине панели лимитов.
- Ожидаемый тариф для каждого провайдера (задаётся по желанию) и проверка аккаунта/тарифа после входа.
- Восстановление живых сессий, включая обе роли Council-пары, после успешного перелогина.

### Out of scope
- Вход по API-ключу, долгоживущий setup-token, смена способа входа и маркировка моделей по тарифу. Это фаза 4 (C.4).
- Мастер первого запуска и вход внутри Docker (фаза 3).
- Выход из аккаунта (logout) из UI.

### Non-goals
- Aura не реализует OAuth сама: вход выполняют официальные CLI, а Aura только передаёт ссылку, код и ответ.
- Aura не хранит пароли и не автоматизирует браузерную страницу провайдера.

## Stories

### Story 1: вход из браузера владельца (B.1)

**When** провайдер требует входа, а Aura работает на сервере, **I want to** пройти вход в своём браузере и закончить его в окне Aura, **so I can** не открывать терминал сервера.

Given провайдер не авторизован или его вход недействителен
When владелец нажимает «Войти» для этого провайдера
Then в течение 10 секунд показаны ссылка для браузера, одноразовый код (если провайдер его выдаёт), поле для ответного кода (если провайдер его требует) и время, до которого попытка действительна

Given ссылка открыта и вход у провайдера подтверждён
When владелец вводит ответный код (Claude) или провайдер подтверждает код устройства (Codex)
Then окно показывает «вход выполнен» с аккаунтом и тарифом, статус провайдера на Diagnostics становится «работает» без ручного «Check», а новые учётные данные принадлежат пользователю сервиса и лежат там, где их читают сессии

Given код просрочен, неверен или относится к другой попытке
When владелец подтверждает
Then показано «код недействителен или просрочен» и кнопка «Начать заново», а прежние учётные данные (даже нерабочие) остались байт-в-байт прежними

Given попытка входа уже идёт (в другой вкладке или из CLI)
When владелец нажимает «Войти» для того же провайдера
Then показана текущая попытка с вариантами «продолжить» и «отменить», и вторая параллельная попытка не запускается

Given владелец нажал «Отмена» или попытка истекла
When окно закрывается
Then процесс входа завершён, на сервере не осталось висящих процессов входа, а учётные данные не изменены

Given вход запущен командой `aura-companion` на сервере
When владелец проходит его
Then шаги, тексты ошибок и итог те же, что в UI, а в выводе нет токенов

### Story 2: не тот аккаунт или тариф (B.2)

**When** вход привязал не тот аккаунт или тариф, **I want to** увидеть это в момент входа, **so I can** переключиться сразу, а не через неделю по расходам.

Given владелец задал ожидаемый тариф провайдера (например, Claude MAX)
When вход завершается с другим тарифом
Then показано явное предупреждение с обоими значениями («ожидался MAX, привязан PRO») и действие «Войти другим аккаунтом». Это же предупреждение видно в статусе провайдера, пока тариф не совпадёт или ожидание не снимут

Given ожидаемый тариф не задан
When вход завершается
Then аккаунт и тариф показаны для подтверждения, без предупреждения

Given тариф не удалось определить без расхода токенов модели
When вход завершается
Then показано «тариф не определён», а не «совпадает»; предупреждения о несовпадении нет

Given сессии этого провайдера фактически пойдут через другой способ входа (например, ключ API в окружении или настройках перекрывает подписку)
When вход по подписке завершается
Then показано предупреждение, какой способ реально будет использован и где он задан

### Story 3: живые сессии выздоравливают после перелогина (B.3)

**When** я перелогинился, **I want to** чтобы открытые сессии и пары продолжили работу, **so I can** не пересоздавать их и не терять контекст.

Given живые сессии провайдера (включая наблюдателя Council-пары) упали с отказом авторизации
When владелец успешно перелогинивается
Then карточка отказа в каждой из них показывает «вход восстановлен» и «Повторить», а следующий ход использует новый вход. Сессию не пересоздают, история и привязка к паре сохраняются

Given у сессии не было отказа и она простаивает
When перелогин завершён
Then её следующий ход тоже идёт на новом входе

Given сессия была посреди хода в момент перелогина
When перелогин завершён
Then ход не обрывается молча: он либо завершается, либо сессия показывает карточку «ход нужно повторить»

Given перелогин не удался или отменён
When владелец возвращается к сессиям
Then ни одна сессия не перезапущена, их состояние не изменилось, и они по-прежнему показывают причину отказа

Given перелогин завершён
When владелец открывает сессии
Then ни один упавший ход не отправлен заново автоматически: повтор только по клику

## Boundaries

### ✅ Always
- Каждая история работает и для Claude, и для Codex. Если у провайдера нет шага (например, ответного кода), UI его не показывает.
- Ссылки входа, коды устройства, ответные коды и токены не попадают в логи, записи протокола, `log.*` и ответы REST, кроме окна самой попытки. Канарейку утечек фазы 1 расширить на поток входа.
- Новые учётные данные записываются атомарно и от имени пользователя сервиса, туда, откуда их читает сервис.
- Каждое действие входа требует аутентифицированной сессии Aura и проходит проверку origin.
- Тесты потоков входа идут против поддельного CLI или изолированного HOME с синтетическими данными. Регрессионные тесты есть на каждый инцидент из Context.

### ⚠️ Ask first
- Механизм, которым живые сессии (особенно Codex с его копией входа на сессию) получают новый вход. Это «изменение того, как сессии получают учётные данные» из родительской спеки: план согласовать до кода.
- Если официальный CLI не позволяет провести вход без терминала (нет device-flow, ответный код нельзя передать программно), остановиться и спросить. Обходной путь не придумывать.
- Изменения systemd-юнита, PATH сервиса или установки CLI.

### 🚫 Never
- Создавать независимые копии ротируемых учётных данных для сессий, проб или тестов.
- Перезаписывать рабочие или текущие учётные данные результатом неудачной, отменённой или просроченной попытки.
- Запускать вход под root или другим системным пользователем вместо пользователя сервиса.
- Проверять вход на проде против реальных учётных данных пользователя сервиса.
- Самостоятельно повторять упавшие ходы после перелогина.

## Success Metrics

### Launch criteria
- Инциденты «мёртвый Claude refresh» и «Codex на сервере + устаревшие копии в сессиях» воспроизведены в тестах и решаются из UI без ssh.
- Вход (без учёта времени на стороне провайдера) от клика «Войти» до статуса «работает» занимает не больше 3 минут. Проверено один раз на живом сервере владельцем для обоих провайдеров.

### 30-day success
- Ноль случаев, когда для входа или перелогина понадобились ssh или tmux.
- Ноль пересозданных сессий или пар из-за перелогина.

## Assumptions

Первые два пункта не подтверждены и проверяются в сессии плана до начала задач. Остальные — рекомендуемые значения по умолчанию, которые владелец принял 2026-11-14.


- `claude auth login` (2.1.283) на хосте без браузера выдаёт ссылку и принимает ответный код, и это можно провести без TTY. Проверить в изолированном HOME до плана. Если нельзя — ⚠️ Ask first.
- `codex login --device-auth` (0.162.1) пригоден для проксирования ссылки и кода через UI (флаг есть, поведение без TTY не проверено).
- Аккаунт и тариф после входа определяются пробой статуса из фазы 1, без расхода токенов модели.
- Ожидаемый тариф — необязательная настройка на провайдера, по умолчанию не задана.
- После перелогина «Повторить» в карточке отказа — по клику, без автоповтора (согласуется с запретом фазы 1 тратить ходы без согласия).
