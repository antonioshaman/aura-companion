# Spec: Отказоустойчивая авторизация LLM-провайдеров (Claude + Codex)

**Date:** 2026-11-13
**Tier:** Product/system · **Status:** Confirmed scope 2026-11-13 (owner answers applied)
**Authorship:** AI-generated; owner approval covers scope, not a code review.
**Related:** `specs/model-registry-and-failover.md` (каталог моделей и замена модели — НЕ дублируется здесь).

## Vision

Владелец Aura не должен знать устройство OAuth у Anthropic и OpenAI, чтобы пользоваться Aura. Установка, первый вход, перелогин, смена тарифа (MAX↔PRO, подписка↔API-ключ), протухший токен, обрыв связи — всё видно и решается внутри Aura (браузер или команда `aura-companion`), без ssh/tmux/tailscale-отладки. Почему сейчас: каждая из этих ситуаций уже случалась на проде, каждая стоила часов ручной диагностики, и каждая выглядела как «сломалась Aura», хотя причина была в авторизации.

## Problem Statement

Сегодня Aura только *пассивно* смотрит на наличие файлов учётных данных. Реальные инциденты:

1. Claude OAuth истёк вместе с refresh-токеном → панель лимитов молча пустеет, автоназвание падает 400; лечится только интерактивным логином в tmux с ручной вставкой кода.
2. Codex-логин на headless-сервере ждёт редирект на `localhost` сервера (не работает из браузера владельца); работает только device-flow, плюс ловушка рабочей директории. Каждая сессия держит свою копию учётных данных — после перелогина живые сессии не выздоравливают.
3. Ротация refresh-токена: любая копия учётных данных (другой HOME, бенч, логин под другим системным пользователем) убивает основную.
4. Привязан не тот аккаунт/тариф (браузер был залогинен в PRO вместо MAX); список моделей строится по API-ключу, а сессии идут по подписке → модель вне тарифа уходит в extra usage → «out of extra usage» при 3% пятичасового окна.
5. Сервис запускает не тот бинарь CLI (PATH, не переключённый симлинк после update) → ошибка «version required», похожая на авторизационную.
6. Ошибки маскируют причину: «Codex protocol drift» вместо `unauthorized`, призрачный баннер «session limit» после сброса окна.

Обходной путь владельца — ssh в сервер и знание этих ловушек. У нового пользователя такого пути нет.

## Target Users

Каждый пользователь Aura — владелец своей установки (owner-confirmed): любой аутентифицированный пользователь UI/CLI имеет права на управление авторизацией провайдеров.

### Сегмент 1: владелец на удалённом сервере (Linux + systemd, браузер на другом устройстве) — приоритет
- **Primary need:** войти/перелогиниться в провайдера, не открывая терминал сервера.
- **Success:** ни один инцидент из списка выше не требует ssh.

### Сегмент 2: локальная установка (macOS / Linux desktop) и Docker-контейнер
- **Primary need:** тот же сценарий установки и восстановления, адаптированный под окружение.
- **Success:** мастер установки проходится до первой рабочей сессии без документации.

## Scope

### In scope (v1)
- Мастер авторизации при установке/первом запуске — для каждого провайдера.
- Единый статус «Авторизация» в UI и CLI + диагностика (`doctor`).
- Вход/перелогин из UI и CLI, работающий на headless-хосте.
- Проактивные предупреждения до отказа сессии.
- Восстановление живых сессий после перелогина без пересоздания.
- Классификация ошибок провайдера с причиной и одним действием.
- Смена способа авторизации и тарифа; соответствие предлагаемых моделей реальной авторизации.
- Резервный способ авторизации — только с явного согласия владельца в момент отказа.
- Три окружения: удалённый сервер, локальная установка, Docker.

### Out of scope (v1)
- Каталог моделей и замена модели — `model-registry-and-failover.md`.
- Пул из нескольких аккаунтов одного провайдера, балансировка между ними.
- Покупка/продление подписок внутри Aura.
- Провайдеры кроме Anthropic и OpenAI (Gonka и др.).
- Внешние уведомления (Telegram, push, email) — владелец отказался 2026-11-13; сигнал только в UI/CLI.

### Non-goals
- Aura не хранит пароли провайдеров и не автоматизирует их браузерный логин.
- Aura не переключается на платный способ автоматически, даже если это «спасло бы» сессию.

## Stories

### Область A — установка и статус

#### Story A.1: первый запуск без авторизации

**When** я устанавливаю и впервые запускаю Aura, **I want to** увидеть по каждому провайдеру, готов ли он, и пройти вход прямо там, **so I can** открыть первую рабочую сессию без документации.

Given свежая установка, где ни Claude, ни Codex не авторизованы
When владелец запускает Aura впервые (CLI или браузер)
Then для каждого провайдера показано «не авторизован» и предложен вход; пропуск провайдера разрешён, и пропущенный провайдер помечен недоступным при создании сессии

Given один провайдер авторизован, другой нет
When владелец завершает мастер
Then создание сессии с неавторизованным провайдером недоступно с пояснением и ссылкой на вход, а с авторизованным — работает

Given CLI провайдера не установлен или его версия ниже требуемой для выбранной модели
When мастер проверяет провайдера
Then показана конкретная причина и действие (установить/обновить), а не «не авторизован»

Given установка в Docker-контейнере
When мастер проверяет провайдера
Then статус отражает учётные данные, которые реально видит контейнер, а не хост

Given сессия запускается в контейнере
When ей нужны учётные данные провайдера
Then она использует единственный экземпляр учётных данных хоста, а не их независимую копию, и перелогин на хосте сразу действует в контейнере

#### Story A.2: понятный статус авторизации

**When** что-то идёт не так с LLM, **I want to** в одном месте увидеть правду об авторизации каждого провайдера, **so I can** понять причину за секунды.

Given авторизованный провайдер
When владелец открывает статус (UI) или выполняет команду статуса (CLI)
Then видны: состояние (работает / скоро истекает / истёк / не авторизован / нет связи), аккаунт, тариф, способ (подписка или API-ключ), срок действия, версия и путь CLI, которым реально запускаются сессии

Given учётные данные присутствуют, но отклоняются провайдером
When статус обновляется
Then состояние «недействительны», а не «авторизован» — наличие файла не считается успехом

Given сервис запускает другой бинарь CLI, чем установлен у пользователя сервиса
When владелец запускает диагностику
Then расхождение показано с обоими путями и версиями и действием по исправлению

Given обнаружена независимая копия ротируемых учётных данных (другой HOME / другой системный пользователь / сэндбокс)
When владелец запускает диагностику
Then показано предупреждение, что копия может инвалидировать основной вход

Given у провайдера нет связи
When статус обновляется
Then состояние «нет связи» с временем последней успешной проверки, и оно не показывается как «истёк»

### Область B — вход и перелогин

#### Story B.1: вход с headless-сервера из браузера владельца

**When** провайдер требует входа, а Aura работает на удалённом сервере, **I want to** пройти вход из своего браузера и ввести код в Aura, **so I can** не открывать терминал сервера.

Given провайдер не авторизован на удалённом хосте
When владелец запускает вход из UI
Then показана ссылка (и, где применимо, одноразовый код) для браузера; поле для ответного кода — в том же окне Aura

Given ответный код введён до истечения его срока
When владелец подтверждает
Then вход завершён, статус показывает аккаунт и тариф, и пользователь сервиса (а не другой системный пользователь) владеет новыми учётными данными

Given код просрочен или от другой попытки входа
When владелец подтверждает
Then показано «код недействителен/просрочен» и предложена новая попытка; прежние рабочие учётные данные не испорчены

Given вход запущен из CLI (`aura-companion`)
When владелец проходит его
Then шаги и результат те же, что в UI

#### Story B.2: не тот аккаунт или тариф

**When** вход привязал не тот аккаунт или тариф, **I want to** сразу это увидеть и переключиться, **so I can** не обнаружить ошибку через неделю по расходам.

Given владелец задал ожидаемый тариф (например MAX)
When вход завершается с другим тарифом
Then показано явное предупреждение с обоими значениями и действие «войти другим аккаунтом»

Given ожидаемый тариф не задан
When вход завершается
Then аккаунт и тариф показаны для подтверждения, без предупреждения

#### Story B.3: живые сессии выздоравливают после перелогина

**When** я перелогинился, **I want to** чтобы уже открытые сессии продолжили работать, **so I can** не пересоздавать пары и не терять контекст.

Given живые сессии провайдера упали на авторизации
When владелец успешно перелогинивается
Then следующий ход каждой такой сессии использует новые учётные данные без пересоздания сессии и без потери истории

Given сессия была посреди хода при перелогине
When перелогин завершён
Then ход не прерывается молча: он либо завершается, либо сессия показывает, что ход нужно повторить

Given перелогин не удался
When владелец возвращается к сессиям
Then их состояние не изменилось, и они по-прежнему показывают причину отказа

### Область C — работа и сбои

#### Story C.1: предупреждение до отказа

**When** авторизация вот-вот сломается, **I want to** узнать заранее, **so I can** перелогиниться до того, как упадёт рабочая сессия.

Given токен истекает в ближайшие 24 часа или его продление не удалось
When владелец открывает UI
Then виден баннер с причиной и действием «перелогиниться»

Given продление прошло успешно
When статус обновляется
Then баннер исчезает

#### Story C.2: ошибка провайдера с причиной и действием

**When** ход падает из-за провайдера, **I want to** видеть, что именно случилось и что нажать, **so I can** не расследовать журналы.

Given ход упал из-за авторизации (в том числе, если CLI сообщил об этом нестандартным кадром)
When ошибка показывается в сессии
Then она названа ошибкой авторизации с действием «перелогиниться», а не «protocol drift» или общей ошибкой

Given ход упал из-за исчерпанного окна подписки (5h / 7d) или extra usage
When ошибка показывается
Then указано, какое именно окно/кошелёк исчерпан, время его сброса и связь с выбранной моделью, если модель вне тарифа

Given окно лимита уже сброшено
When владелец открывает сессию
Then устаревший баннер лимита не показывается и не блокирует отправку сообщения

Given провайдер недоступен по сети
When ход падает
Then показано «нет связи с провайдером», ход можно повторить одним действием, и это не помечается как проблема авторизации

#### Story C.3: резервный способ — только с согласия

**When** основной способ авторизации отказал, а резервный настроен, **I want to** чтобы Aura спросила меня, переключиться ли, **so I can** контролировать расходы.

Given подписка отказала (истекла, отменена или лимит исчерпан), а API-ключ того же провайдера настроен
When ход падает
Then Aura предлагает продолжить на API-ключе, указывая, что это платно, и ничего не переключает без подтверждения

Given владелец подтвердил переключение
When следующий ход выполняется
Then он идёт по резервному способу, и способ виден в статусе сессии

Given владелец отказался или не ответил
When ход повторяется
Then способ авторизации не меняется

#### Story C.4: смена способа авторизации и модели под неё

**When** я перехожу между подпиской и API-ключом или между тарифами, **I want to** чтобы Aura предлагала только модели, доступные текущему способу, **so I can** не получить «out of extra usage» на ровном месте.

Given сессии авторизованы подпиской
When владелец открывает выбор модели
Then модели вне тарифа помечены как недоступные или платные (extra usage), а не показаны как обычные

Given владелец меняет способ авторизации провайдера
When сохраняет изменение
Then новые сессии используют новый способ, а для живых сессий показано, что изменение применится после перезапуска или следующего хода

## Technical Context

- **Существующие системы:** локальная детекция статуса, данные о лимитах использования, распознавание ошибок авторизации в сообщениях, логика авторизации при запуске и перезапуске сессий, онбординг, CLI `aura-companion` (install/start/status/...).
- **Провайдеры:** Claude Code CLI (OAuth подписки, setup-token, API-ключ), Codex CLI (ChatGPT-логин включая device-flow, API-ключ). Все провайдерские потоки входа выполняются официальными CLI, а не собственной реализацией.
- **Ограничения:** refresh-токены ротируются и одноразовы; на хосте сервис работает от отдельного системного пользователя; обе CLI обязаны поддерживаться одинаково (CLAUDE.md, раздел «Codex & Claude Code»).

## Boundaries

### ✅ Always
- Каждая история реализуется для Claude и Codex; если провайдер не поддерживает возможность — она скрыта с пояснением.
- Секреты (токены, ключи, коды) редактируются из логов, записей протокола, UI и уведомлений.
- Операции записи учётных данных атомарны и выполняются от имени пользователя сервиса.
- Регрессионные тесты на каждый инцидент из Problem Statement.

### ⚠️ Ask first
- Любое изменение того, как сессии получают учётные данные при запуске или перезапуске.
- Изменения systemd-юнита, PATH сервиса или способа установки CLI.
- Добавление любого нового внешнего сервиса.

### 🚫 Never
- Создавать независимые копии ротируемых учётных данных (для сэндбоксов, тестов, сессий).
- Автоматически переключаться на платный способ авторизации без подтверждения в момент отказа.
- Перезаписывать рабочие учётные данные результатом неудачной попытки входа.
- Тестировать вход на проде против реальных учётных данных пользователя сервиса.

## Success Metrics

### Launch criteria (v1 is done when)
- Каждый из 6 инцидентов Problem Statement воспроизводится в тесте и решается из UI без ssh.
- Чистая установка в каждом из трёх окружений проходит до первой рабочей сессии с обоими провайдерами.

### 30-day success
- Ноль случаев, когда владельцу понадобился ssh/tmux для авторизации.
- Каждый отказ авторизации на проде показан баннером раньше, чем владелец заметил его по упавшей сессии.

## Recommended Decomposition

### Phase 1 — правда о состоянии
- A.2 + C.2 — без верного статуса и классификации ошибок остальное строить не на чем.

### Phase 2 — вход без терминала
- B.1 + B.2 + B.3 — главный источник «танцев с бубном».

### Phase 3 — установка
- A.1 для трёх окружений — использует вход из Phase 2.

### Phase 4 — проактивность и резерв
- C.1 + C.3 + C.4.

Каждую фазу перед реализацией развернуть в отдельную feature-спеку.

## Assumptions

- Любой аутентифицированный пользователь Aura — владелец установки и вправе управлять авторизацией (confirmed).
- Резерв — только по подтверждению (confirmed).
- Охват: сервер, локальная установка, Docker (confirmed; приоритет — сервер).
- Внешних уведомлений нет (confirmed).
- Порог «скоро истекает» — 24 часа (confirmed).
- Docker — вторичный сценарий (владелец его не использует); принят вариант «контейнер на учётных данных хоста без копии, вход на хосте» (recommended default, unconfirmed by a Docker user).
- Официальные CLI предоставляют неинтерактивный или device-flow вход, пригодный для проксирования через UI (unconfirmed — проверить для текущих версий).
- Тариф и аккаунт можно определить без расхода токенов модели (unconfirmed).

## Open Questions

- Docker: подтвердить у реального Docker-пользователя, что вход на хосте (а не внутри контейнера) удобен. Сегодня Aura копирует файлы авторизации в контейнер — это нарушает правило «Never» и должно быть заменено в фазе 3.
