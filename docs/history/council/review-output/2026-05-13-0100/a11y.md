## P1 — `lastIdsRef` resets across mount/unmount, re-announcing existing findings on every collapse/expand

**File:** `web/src/components/council/FindingsLog.tsx` lines 200–214.

**User impact:** Screen-reader user. The user collapses the ObserverPanel (panel state `observerPanelOpen[sessionId] = false`), which **unmounts** `FindingsLog` (in `ObserverPanel.tsx` line 213 the entire `<aside>` is replaced by `<CollapsedRail/>`). When the user expands the panel again, `FindingsLog` remounts, `lastIdsRef` is initialised to `new Set()`, and the effect runs with EVERY existing finding treated as "new." The summary announcer fires `"Observer review complete: N blockers, M notes"` — but nothing actually arrived. The SR user is told findings are new when they are stale.

This is the exact failure mode the cadence-aware refactor was designed to prevent (3–8 announcements per checkpoint), just triggered by panel collapse/expand instead of by per-row appends. Worse, the user explicitly chose to dismiss the panel, then chose to re-open it — they expect quiet, they get a fresh review-event announcement.

The same hazard fires on:
1. Panel collapse → expand cycle (the load-bearing case — users collapse the panel to focus on chat).
2. Sidebar session switch back to a Council session whose panel had been open (Zustand state survives but the React subtree is re-rendered).
3. React 19 Strict Mode dev double-invocation (less load-bearing but explains "why does the announcer fire twice in dev").

**Evidence the test does not cover this:** `FindingsLog.test.tsx:108–121` re-renders with `rerender(...)`, which keeps the component mounted. There is no unmount+remount test, and no test asserting the announcer is **empty** after remount with no new findings.

**Severity rationale:** Streaming-content with surprise-re-announcement is a P1 in Principle 3 (this is the moral equivalent of `aria-atomic="true"` on a streaming bubble — the user gets the whole thing read again).

**Fix shape (no code per finding rules, just direction):** persist `lastIdsRef` across mount via either (a) lifting the seen-ids set up to the parent council slice as `announcedFindingIds: Map<groupId, Set<findingId>>` so it survives unmount/remount and cross-session navigation, or (b) hydrating `lastIdsRef.current` on first effect run with the current `findings` ids and a separate `hasRunRef` boolean — but only if you accept "we never announce the first paint of a remounted panel," which is fine because remount ≠ new review. Option (a) is the durable choice (sibling of the "in-memory derived state must reconcile on restart" idiom). Add a test: render → unmount → re-mount with same `findings` → announcer must be empty.

## P2 — Empty-string `<div role="status">` on first mount makes some SR engines announce "blank"

**File:** `web/src/components/council/FindingsLog.tsx` lines 201, 216–226.

**User impact:** Screen-reader user. `useState<string>("")` renders the announcer as `<div role="status" aria-live="polite" aria-atomic="true">""</div>` from the moment the panel mounts. NVDA and JAWS handle empty text content fine, but **VoiceOver on macOS** has a long-standing quirk where `role="status"` regions with empty initial content sometimes get announced as "blank" or "status" when the SR cursor first enters the page. Less critically, when `announcement` is later cleared (which currently never happens, so this is latent — but would matter if someone added a "clear on review-completed" reset).

The bigger concern: `aria-atomic="true"` paired with `role="status"` (which implies `aria-live="polite"`) on a region that starts empty means the very FIRST review announcement is the first time the region transitions from empty → text. Most SR engines handle that correctly, but the convention from APG is to render the announcer node only when there is something to announce, OR use `aria-relevant="additions text"` to be explicit.

**Severity rationale:** Significant-friction-but-not-blocker; SR-engine-dependent. P2 in Principle 3.

**Fix shape:** conditional render (`{announcement && (<div role="status" …>{announcement}</div>)}`), OR keep the always-mounted node but add `aria-relevant="additions text"` and ensure the initial state is truly empty (no whitespace, no `​`). Add a test: on initial render with empty findings, `screen.queryByTestId("findings-review-announcer")?.textContent` should be exactly `""` (currently passes, but make it an explicit assertion so a regression to `" "` is caught).

## P2 — New test pack covers cadence but NOT focus-management; prior a11y rec ("BlockerBanner no-focus-move") still untested at the integration boundary

**File:** `FindingsLog.test.tsx`, `ObserverPanel.test.tsx` (whole files).

**User impact:** Keyboard-only user. CLAUDE.md mandates `toHaveNoViolations()` on every component test (satisfied — `FindingsLog.test.tsx:178–196` and `ObserverPanel.test.tsx:310–353` have axe scans at four+ states including new `reconnecting`). However, the question posed in the brief — "do they cover focus-management (BlockerBanner no-focus-move was an a11y rec)?" — the honest answer is **no**.

What is tested:
- `aria-live="off"` attribute on the row container.
- Summary announcer attributes (`aria-live="polite"`, `aria-atomic="true"`).
- `1 blocker`, `1 note` substring presence.
- Singular/plural via `buildFindingsReviewSummary` (pure function, presumably has its own unit tests — not in scope here).
- axe scans at 4 panel states.

What is NOT tested:
- That announcement does not move focus (a load-bearing claim of `role="status"`: it must NOT pull focus, only announce).
- That a STOP arriving while focus is in `Composer` does not yank focus into the panel.
- That `Cmd/Ctrl+Shift+B` (the BlockerBanner-focus shortcut from CLAUDE.md) is the OPT-IN way to move to the banner, not arrival.
- That the `reconnecting` and new state pills (`reviewing-stalled`, `queued-dropped` per the brief) have axe scans. Spot check: the test file shows axe scans for `sleeping`, `blocker-found`, `degraded`, `collapsed-rail`, AND `reconnecting` (ObserverPanel.test.tsx:151–178). `reviewing-stalled` and `queued-dropped` axe scans are **not** present in this file. If those states render in `ObserverPanel.tsx`'s `StatusPill` switch (or `BlockerBanner` rendering changes for them), they need their own axe pass.

**Severity rationale:** P2 per Principle 1 ("Test passes axe but doesn't actually exercise a11y"). The render-only axe pass is necessary-not-sufficient for focus correctness. The brief explicitly asked the question and the answer is "the new tests are cadence-only."

**Fix shape:** add (a) a focus-management test — render `ObserverPanel` with `seedReview({stopIds:["x"]})` and assert `document.activeElement` did NOT change (still `document.body` or composer); (b) axe scans for any new state variants surfaced by `deriveObserverPanelState` (`reviewing-stalled`, `queued-dropped`) if those produce visually-distinct pill content. If `StatusPill` doesn't have explicit cases for those state names yet, that's a separate finding for the React UI lane — out of scope here, just flag the test gap.

## P3 — `role="status"` on the announcer is redundant with `aria-live="polite"`; pick one to avoid SR engines double-announcing

**File:** `web/src/components/council/FindingsLog.tsx` lines 217–220.

**User impact:** Screen-reader user (NVDA + Firefox specifically). `role="status"` is an ARIA shorthand for `aria-live="polite" aria-atomic="true" role="status"`. Setting all three explicitly is supported but historically NVDA has been observed to announce twice in this combination (once for the role-implied live region, once for the explicit attribute). APG's `Alert and Message Dialogs` example uses `role="status"` alone, no explicit `aria-live`. Marcy Sutton's recommendation is "pick the role OR the attributes — don't double-declare."

**Severity rationale:** P3 polish; modern NVDA versions have fixed the double-announce. Worth knowing about, not urgent.

**Fix shape:** drop `aria-live="polite"` since `role="status"` already implies it (keep `aria-atomic="true"` — that one is NOT implied by `role="status"` despite some sources claiming otherwise). Alternatively drop `role="status"` and keep the explicit attributes — same outcome semantically. Choose one and document the choice in the comment block at line 185–199.

## P3 — `aria-atomic="true"` on the summary IS correct for this cadence; confirming

**File:** `web/src/components/council/FindingsLog.tsx` line 220.

**Confirmation, not a finding.** The brief asks if `aria-atomic="true"` is correct for re-reading the whole summary each time. **Yes.** The summary string is a fixed-shape sentence ("Observer review complete: N blockers, M notes"); the user benefits from hearing the full sentence on each review event rather than just the diff (which would be unintelligible: "blocker" with no count). This is the inverse of the streaming-token case in Principle 3 where `aria-atomic="true"` is a P1 — the streaming concern is "atomic on a region that grows token-by-token causes re-read." The announcer here is "atomic on a region that snapshot-replaces on each batched event," which is exactly the APG-recommended pattern.

The cadence-aware refactor is correct in shape; only the remount-replay bug (P1 above) prevents it from being right in practice.
