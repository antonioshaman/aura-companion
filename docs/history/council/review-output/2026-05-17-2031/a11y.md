# a11y Auditor — Council Review Findings

PR scope: docs-only rebrand + Council Mode coverage. Domain: `landing/src/components/Nav.tsx`, `landing/src/components/Footer.tsx`, `README.md`, `docs/index.mdx`, `docs/guides/council-mode.mdx`. Reference: WCAG 2.2 AA + APG. Anchors: Principle 1 (axe-floor), 5 (roles/names), 8 (motion), 10 (gap awareness); plus content-side equivalents for Markdown/MDX (alt text, heading hierarchy, table semantics, link `rel` hygiene).

---

## P1 findings

### P1-A11Y-01 — Icon-only logo anchor in Nav has no accessible name disambiguated from the brand wordmark

**File:** `landing/src/components/Nav.tsx:7-10`
**Severity:** P1
**Principle:** Roles, names, and accessible labels (Principle 5).

**Finding.** The home-link anchor wraps `<ClawdLogo size={28} />` and the visible text "Aura Companion". The logo is an SVG/img component whose internal a11y is not visible at this call-site — if `ClawdLogo` renders an `<svg>` without `aria-hidden="true"` (or a `<img>` without `alt=""`), the link's accessible name will concatenate the SVG's computed name with the wordmark ("Aura Companion logo Aura Companion") and a screen-reader announces the brand twice. If `ClawdLogo` is silent (`aria-hidden`), the anchor is fine — but the call-site does not assert it.

**Consequence.** Screen-reader users hear the brand stuttered ("Aura Companion Aura Companion link") on every page load and on every Tab pass through the nav. Sighted users are unaffected; this is a SR-only friction that compounds on a multi-page landing site.

**Fix.** Either (a) inspect `ClawdLogo` and confirm it renders with `aria-hidden="true"` on the root SVG/img, OR (b) at the call-site wrap the logo in a `<span aria-hidden="true">` and rely on the wordmark for the accessible name. Add a Vitest+axe render assertion on `<Nav />` that asserts `getByRole("link", { name: /aura companion/i })` matches exactly once, not twice — this is the EC-6 static canary against future logo-component drift.

### P1-A11Y-02 — README screenshot anchor `<p align="center">` inserts an `<img>` whose container is layout-only, no surrounding landmark

**File:** `README.md:1-3` (hero), `README.md:29` (overview)
**Severity:** P1
**Principle:** Axe is a floor (Principle 1) — GitHub renders MD differently than docs site; `<p align="center">` is presentational and the image becomes a top-of-document figure with no figure semantics.

**Finding.** The hero screenshot lives in a centered `<p>` with no `<figure>`/`<figcaption>`. The alt text ("Aura Companion main workspace with Council Mode toggle on the New Session dialog", 80 chars) is descriptive and within budget — but the image stands as a 100%-wide hero with no programmatic relationship to the H1 that follows it. A screen-reader user lands on the page and hears `image, Aura Companion main workspace...` before any heading announces what the page is. The same applies to the overview screenshot (`README.md:29`, 92 chars) which sits between two H2 sections with no caption tying it to either.

**Consequence.** First-time SR users get image content before page identity. The overview image is also ambiguously associated — does it illustrate "Why Council Mode" (the H2 above) or "Quick Start" (the H2 below)? Sighted users resolve this with whitespace; SR users cannot.

**Fix.** Wrap each hero/inline screenshot in a `<figure>` with a `<figcaption>` that names what is shown (one short sentence — can re-use the alt text or summarise differently). On GitHub, `<figure>` renders as a block; on Mintlify, same. This also satisfies the WCAG 1.3.1 (Info and Relationships) requirement that visual grouping be programmatically determinable.

## P2 findings

### P2-A11Y-01 — Double-H1 risk: `docs/index.mdx` has Mintlify front-matter `title` AND an in-body `# Aura Companion`

**File:** `docs/index.mdx:1-7`
**Severity:** P2
**Principle:** Heading hierarchy (Principle 5 — roles and names extended to landmarks).

**Finding.** Lines 1-4 declare front-matter `title: Aura Companion`. Mintlify renders this as the page H1. Line 6 then writes a second `# Aura Companion`. Depending on the Mintlify version's MDX renderer, the in-body `#` will either (a) become a second H1 (two H1s per WCAG 1.3.1 best-practice violation, SR users hear "Aura Companion, heading level 1" twice in sequence) or (b) be silently demoted to H2 — at which point the document hierarchy starts at "Quick start" as H2 which is correct only by accident.

**Consequence.** Either two H1s in the SR landmark list (confusing) or fragile hierarchy that depends on the renderer's silent demotion behaviour (drifts on Mintlify upgrade). `docs/guides/council-mode.mdx:1-7` has the identical pattern (`title:` + `# Council Mode`) and the same risk.

**Fix.** Drop the in-body `# Aura Companion` (and `# Council Mode`) — the front-matter `title` is the SSOT for the H1 on Mintlify. Verify by previewing the Mintlify build and inspecting `document.querySelectorAll("h1")` returns exactly one node per page. Add a CI canary if Mintlify exposes one: `grep -E "^# " docs/**/*.mdx` should return zero matches under front-matter docs.

### P2-A11Y-02 — Council Mode tables have no `<caption>` and no scoped headers

**File:** `docs/guides/council-mode.mdx:48-51` (pairings), `:73-76` (shortcuts), `:147-155` (troubleshooting)
**Severity:** P2
**Principle:** Roles and names (Principle 5) — tables need caption + scope for SR table-navigation mode.

**Finding.** Three GFM-style tables render as `<table><thead><tr><th>...</th></tr></thead><tbody>...</tbody></table>`. Mintlify/GFM does not auto-emit `<caption>` and the `<th>` cells default to `scope="col"` only on some renderers — and never `scope="row"` for the first-column "key" cells (Pairing, Shortcut, Symptom). SR users entering table-navigation mode hear cells with no caption announcing what the table is about, and row-headers are not announced as headers when navigating cells across rows.

**Consequence.** The troubleshooting table is the worst case: a 7-row, 3-column matrix where the SR user needs to navigate cell-by-cell to triage a symptom. Without `scope="row"` on the Symptom column, they lose track of which row they are on. Without a caption, they have no idea this is the troubleshooting table vs the pairings table vs the shortcuts table.

**Fix.** Mintlify/MDX does support raw `<table>` blocks with explicit `<caption>` and `<th scope="row">`. For tables this load-bearing, switch from pipe-table syntax to raw HTML in the MDX with: `<caption>Council Mode pairing options</caption>`, `<caption>Council Mode keyboard shortcuts</caption>`, `<caption>Council Mode troubleshooting</caption>`, plus `<th scope="row">` on the first cell of each `<tbody>` row. Saarinen's table-density framing is orthogonal — captions and scope cost zero visual density.

### P2-A11Y-03 — `hidden sm:block` GitHub link in Nav makes GitHub unreachable for mobile keyboard users

**File:** `landing/src/components/Nav.tsx:12-19`
**Severity:** P2
**Principle:** Keyboard navigation (Principle 7) + Know your gaps (Principle 10, mobile).

**Finding.** The plain-text "GitHub" link uses `hidden sm:block`, so it disappears below 640px. The styled "Open Repo" CTA (lines 20-27) remains — but only that one. Mobile keyboard users (Bluetooth-keyboard tablet, foldable in landscape under 640px, browser zoom at 200%+ which triggers responsive breakpoints per WCAG 1.4.4) lose one of two equivalent paths and have only the CTA. Worse, the `hidden` class on `<a>` removes it from BOTH the visual layout AND the tab order (`display: none` semantics) — sighted-keyboard users on mobile can't shift-tab back to it.

**Consequence.** Two issues: (a) zoomed-desktop users (200%, 400%) hit the mobile breakpoint and lose the plain link, which is the more conventional "go to source" affordance; (b) the redundancy that was intentional on desktop (text link + button) collapses to button-only on mobile, reducing affordance discoverability. This is also a minor WCAG 1.4.10 (Reflow) consideration.

**Fix.** Either show both anchors on mobile (the styled CTA at smaller sizing — drop the `hidden sm:block`), or accept the loss as a design call but document it. If kept, ensure the "Open Repo" CTA's accessible name is unambiguously "GitHub repository" (currently "Open Repo" — see P3-A11Y-01 below).

### P2-A11Y-04 — Ordered-list state-pill priority in council-mode.mdx encodes priority but loses the "top wins" semantic for SR users

**File:** `docs/guides/council-mode.mdx:60-69`
**Severity:** P2
**Principle:** Roles and names (Principle 5) — ordered list semantics imply sequence, not priority.

**Finding.** The PR replaced a table with an ordered list of 7 ObserverPanel states, prefixing each with "1." through "7." and an inline note "priority ladder (top wins)". The ordered list `<ol>` semantic announces "list, 7 items, item 1 of 7, degraded" — which a SR user interprets as ordered SEQUENCE (do these in order). The prose above the list does state "priority ladder ('top wins')", but the list itself carries no programmatic semantic for priority.

**Consequence.** Mid-document SR navigation by heading lands the user inside the list with no priority-cue. The visually-encoded "earlier = higher priority" idiom is not announced; users hear seven equally-weighted states in arbitrary-looking sequence.

**Fix.** Two options. (a) Keep the `<ol>` but introduce each item with the priority rank as visible content ("Highest: degraded — ...", "Then: blocker-found — ..."), so the priority is part of the announced text rather than implied by list position. (b) Switch to a `<table>` with `<caption>ObserverPanel state priority (top wins)</caption>` and columns "Priority", "State", "Meaning" — this is one of the rare cases where a table is more accessible than a list because the priority IS the load-bearing dimension. Saarinen's "list over table" framing applies when ordering is sequential; here ordering is ranked, which is table territory.

### P2-A11Y-05 — `target="_blank"` external anchors in Nav and Footer don't announce that they open a new tab

**File:** `landing/src/components/Nav.tsx:12-27`, `landing/src/components/Footer.tsx:6-21`
**Severity:** P2
**Principle:** Roles and names (Principle 5) — external-link semantics.

**Finding.** Six anchors use `target="_blank" rel="noopener noreferrer"` (the PR correctly hardened `rel` — that's not the issue here). None carry visible "(opens in new tab)" text or a sr-only equivalent, and none use `aria-label` to announce the new-tab behaviour. WCAG 3.2.5 (Change on Request) requires that link behaviour be predictable; opening a new tab is an unannounced context change.

**Consequence.** SR users activating "GitHub" or "Open Repo" or the Footer's "MIT License" link don't know a new tab opened. They keep navigating, get confused when content doesn't match, and have no way to know they need to switch back to the original tab. This is one of the most common axe-floor passes (the rule is `target-blank-noopener`, not `target-blank-announced`).

**Fix.** Add a visually-hidden span to each external anchor: `<span className="sr-only"> (opens in new tab)</span>`. Tailwind's `sr-only` utility is the canonical hide-from-sighted-users-only pattern. Apply uniformly across Nav's two anchors and Footer's three external anchors. Out-of-scope but worth noting: the README's outbound links (lines 17, 41, 210, 213-215) are markdown auto-rendered without target=_blank on GitHub, so this finding is landing-only.

## P3 findings

### P3-A11Y-01 — "Open Repo" CTA label is vague — accessible name does not say where it goes

**File:** `landing/src/components/Nav.tsx:20-27`
**Severity:** P3
**Principle:** Roles and names (Principle 5) — name reveals destination.

**Finding.** The styled CTA renders the text "Open Repo". An SR user hears "Open Repo, link". Combined with the duplicate `href` (same URL as the GitHub link), it's redundant in role but the label "Open Repo" is less informative than "GitHub repository". On mobile (where the plain "GitHub" link is hidden — see P2-A11Y-03), this is the only repository link and its label is least informative.

**Consequence.** Minor SR friction. The first-time visitor doesn't know which platform "the repo" is on without context from the surrounding visual treatment (button vs link).

**Fix.** Either change visible text to "Open on GitHub" / "GitHub Repository", or add `aria-label="Open Aura Companion on GitHub"` to the CTA. Visible-text fix is preferred (avoids label-duplication warning per Principle 5 and benefits sighted users too).

### P3-A11Y-02 — Footer MIT-attribution sentence is one long line of mixed inline anchors with no visual or semantic grouping

**File:** `landing/src/components/Footer.tsx:4-14`
**Severity:** P3
**Principle:** Roles and names (Principle 5) + Visual structure.

**Finding.** The attribution `<p>` interleaves three pieces of information (fork source repo, fork source organisation, MIT marker) as a single sentence with two inline anchors. SR users navigating link-by-link hear "The-Vibe-Company/companion, link" then "The Vibe Company, link" with no context. The MIT marker "(MIT)" is plain text but is semantically related to those links.

**Consequence.** Mild friction. The MIT-attribution requirement (Hunt domain) is preserved — this finding is presentational on top of that legal requirement.

**Fix.** Out-of-scope to refactor the prose, but consider wrapping the attribution in a `<small>` element to signal subordinate metadata semantically — both SR and visual readers benefit from the cue. No content change required.

### P3-A11Y-03 — `docs/index.mdx` image embed uses raw `<img>` instead of MDX-idiomatic component

**File:** `docs/index.mdx:10`
**Severity:** P3
**Principle:** Axe-floor (Principle 1) — image semantics under MDX.

**Finding.** The screenshot uses raw `<img src="./screenshots/aura-companion-hero.png" alt="..." width="100%" />`. Alt text (80 chars) is appropriate. Width is a layout attribute (presentational) rather than a CSS class — works, but bypasses Mintlify's responsive-image handling. No `loading="lazy"` either; for an above-the-fold hero that's correct (don't lazy-load LCP image), but for the lower-page screenshots in `docs/guides/council-mode.mdx:10` the same call should arguably set `loading="lazy"` for performance + reduced-motion-friendly (don't trigger layout shift on scroll).

**Consequence.** Performance + CLS hint to assistive tech. SR users are unaffected; low-bandwidth users see slower hero on the guides page.

**Fix.** Add `loading="lazy"` to the council-mode guide screenshot (`docs/guides/council-mode.mdx:10`). Leave hero (`docs/index.mdx:10`) as eager. Consider Mintlify's `<Frame>` component if it exists in this Mintlify version (renders a `<figure>` with consistent spacing — see P1-A11Y-02 for the figure framing rationale).

## Notes on what the PR did right

- Both alt-text strings (`README.md:2`, `:29`; `docs/index.mdx:10`; `docs/guides/council-mode.mdx:10`) are within the ≤125-char budget (80 and 92 chars), convey purpose rather than inventory ("with Council Mode toggle on the New Session dialog", "surfacing a STOP finding"), and avoid the alt-text anti-pattern of "screenshot of...". This is the strongest part of the PR.
- All six `rel="noopener noreferrer"` edits in `landing/src/components/Nav.tsx` and `landing/src/components/Footer.tsx` are correct — `noopener` blocks `window.opener` exploitation, `noreferrer` blocks the Referer leak; both belong on `target="_blank"` external anchors. No new a11y debt introduced by the `rel` hardening itself.
- The ordered-list-encodes-priority swap (`docs/guides/council-mode.mdx:60-69`) is the right direction (table density was real), but the priority semantic needs to be in announced text — see P2-A11Y-04.
- Heading hierarchy below H1 in `docs/guides/council-mode.mdx` is clean (H2 → no skips to H4), aside from the double-H1 risk flagged in P2-A11Y-01.
- README compressed badges 4 → 2 (`README.md:8-11`) with proper `<img alt="...">` on both — no decorative-image-as-content debt.
