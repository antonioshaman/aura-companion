## NEW Findings

### P2 — `councilGroupBySessionId` reverse index leaks on per-session archive/delete of a council half

**File:** `web/server/session-orchestrator.ts` (mutation sites at lines 820-821, 1013-1014, 1934-1935; archive/delete paths at 2376-2425 and 2429-2445).

**Failure mode.** The reverse index is documented to clear on `group:exited` (line 363 doc + listener at 997-1018). The coordinator emits `group:exited` from exactly two paths: `applyEvent` after a `user_archived` event in `archiveGroup`, and `applyEvent` after a `degraded` settles into `archived`. The per-session REST surface (`DELETE /sessions/:id`, `POST /sessions/:id/archive`, both in `routes.ts:1124-1200`) routes to `orchestrator.archiveSession` / `deleteSession`, which add the sessionId to `intentionalKills` and kill the session directly without going through the coordinator. The `session:exited` listener at line 1046 then short-circuits on the `intentionalKills` check (line 1047) and returns. `group:exited` is never emitted; `councilGroupBySessionId.delete(...)` is never called for that sessionId. The companion `councilGroupMeta` and `councilWatchers` entries also persist (same listener owns those teardowns).

Consequence: a council half archived/deleted via the per-session endpoint leaves a stale `sessionId → groupId` entry in the reverse index. Subsequent reuse of the sessionId (delete is followed by `removeSession`; archive keeps the id and the user can later create a new council group reusing different sessionIds, but the orphan stays) means the `observer:turn-done` listener at line 420 will resolve `groupId` from the orphan, fetch a no-longer-existing meta, and `meta` will be undefined — the guard at line 428 absorbs that case, so no functional drain misfire today. The real cost is (a) the map grows monotonically across many archive cycles, (b) the documented invariant ("Maintained alongside councilGroupMeta writes; cleared on group:exited") drifts from runtime truth, and (c) any future code that trusts `councilGroupBySessionId` membership as an "is council session" predicate inherits the drift silently.

**Recommendation.** Either guard the per-session archive/delete REST endpoints when the target is a council half (return 4xx with "use POST /groups/:id/archive instead"), or have `archiveSession` / `deleteSession` inspect `councilGroupBySessionId.get(sessionId)` and route through `coordinator.archiveGroup` when set. The second option is the structurally cleaner one — it matches the EC-2 invariant that group-aware kills mark both halves intentional and emits `group:exited` through the single channel that owns reverse-index + watcher + sentinel cleanup. Bonus: it also closes the orphan-watcher leak on the same code path.

### P3 — `scanForMissedObserverWakes` runs synchronously on `initialize()` and scales O(groups × checkpoint-files)

**File:** `web/server/session-orchestrator.ts:676-736`, called from `initialize()` at line 657.

**Failure mode.** The scan iterates every entry in `councilWatchers`, runs `readdirSync` on each `.council/checkpoints/` dir, then `readFileSync` + `parseCheckpointPayload` on every `.json` file in each dir. All sync I/O on the Bun main thread, all inside the synchronous `initialize()` path. The dispatch path inside the loop (`this.dispatchObserverWake`) is itself sync but only fires once per group (highest-sequence file). The scan blocks server startup until all checkpoint files for all reconciled groups have been read and parsed.

Today's scale this is invisible: typical local dev has 1-3 groups with single-digit checkpoint files each. The risk is concentrated in two regimes: (a) a workspace with months of `.council/checkpoints/` accumulation under a single group (no rotation policy is in place for checkpoint files that I can find), and (b) a developer with many archived workspaces whose `councilWatchers` gets restored across a server upgrade. The dispatcher's structured log line "catchup wake fired for missed checkpoint" lands inside the synchronous loop, so a long scan also delays the first log emission past server-readiness — operator observability degrades just when restart diagnosis matters.

**Recommendation.** Two cheap options. (a) Wrap the body in `queueMicrotask(() => this.scanForMissedObserverWakes())` or `setImmediate(...)` so initialize returns and the bus is wired before the disk pass starts; the dispatcher's Gate 0 sentinel check absorbs any race with a fresh real-time checkpoint that lands during the scan. (b) Cap the per-group file enumeration at e.g. the last 50 by mtime — the watcher only cares about the highest-sequence file, and stale checkpoints below that have no actionable outcome. Either works; (a) is one line.

### P3 — `scanForMissedObserverWakes` mutates `entry.lastCheckpoint` / `entry.previousCheckpoint` without guarding against an in-flight real-time checkpoint

**File:** `web/server/session-orchestrator.ts:725-727`.

**Failure mode.** The scan unconditionally sets `entry.previousCheckpoint = entry.lastCheckpoint; entry.lastCheckpoint = highest;` before calling `dispatchObserverWake`. `initialize()` is called once, very early, before any external trigger could populate `lastCheckpoint` — so the unconditional overwrite is safe today. But the method is private with no caller-side enforcement of the "init-only" assumption, and the doc comment ("EC-12 — fs.watch is event-only, needs pre-scan reconcile") frames it as a pattern that could be re-applied. A future re-call (e.g. after a watcher rearm on relaunch, which is the natural extension) would clobber a real-time `lastCheckpoint` with the highest on-disk value, which may not be the same checkpoint — the watcher's debounce + LRU dedup could have advanced `lastCheckpoint` past `highest` if the file mtime ordering doesn't match sequence ordering.

**Recommendation.** Either inline-document "do not call after initialize" at the top of the method (the simplest fix, matches the current single call site), or guard with `if (highest.sequence > (entry.lastCheckpoint?.sequence ?? -1))` before the mutation. The latter is one cheap line and makes the method genuinely re-callable, preserving the safety property the EC-12 pattern was supposed to give.
