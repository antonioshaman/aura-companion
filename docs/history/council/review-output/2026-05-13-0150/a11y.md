## Confirmation of prior-fix landings (no new findings; verification only)

- **Cross-mount announcer coalescing (prior a11y #10).** Module-level
  `ANNOUNCED_FINDING_IDS_BY_SCOPE` Map keyed by `announcerScope` survives
  FindingsLog unmount/remount cycles. `ObserverPanel` passes
  `group.sessionGroupId` as the scope (line 345), giving each Council
  pair its own announce ledger. Walk-through of the four interesting
  remount paths:
  1. *Collapse → re-expand with no new findings.* useEffect re-runs on
     the new mount; `newOnes` is empty (early return); `announcement`
     stays at the initial `""`; the announcer div is not rendered. No
     re-announcement. Confirmed.
  2. *Collapse → new findings arrive while collapsed → re-expand.* New
     mount loads `seen` from the module map; `newOnes` is exactly the
     ids that landed during the collapse window; `setAnnouncement(...)`
     fires for those only; the announcer mounts with their summary. SR
     hears just the new ones. Confirmed.
  3. *Two Council groups in the same tab.* Distinct
     `group.sessionGroupId` → distinct Map entries; one group's
     announce history does not gag the other's. Confirmed.
  4. *Hard remount (e.g. dev HMR / unrelated parent re-key).* Same as
     case 2 — the module Map outlives the component. Confirmed.
  The "never freed" caveat in the comment block is bounded by page
  lifetime; not a leak in any practical sense — flag only if a future
  long-lived session shows growth, no action now.

- **Conditional render of empty announcer (prior a11y #20).** The
  `<div role="status">` is rendered iff `announcement.length > 0`.
  After the first non-empty render the local state never flips back to
  `""` (no `setAnnouncement("")` path exists), so within a single
  mount the announcer never disappear-and-reappears mid-session — that
  failure mode (which would re-announce stale content) cannot occur.
  Across unmount/remount, the announcer is correctly absent on remount
  when there are no new findings (case 1 above). No new concern.

- **Clock-tick SR impact (prior React #4 + EC-11).** The 1s
  `setInterval` fires `setClockTick`, which re-renders ObserverPanel.
  The two live regions inside the panel are the `reconnecting` pill
  (`role="status"`) and the `reviewing-stalled` pill (`role="status"`).
  Walked the rendered text for both across ticks:
  - `reconnecting` pill content: literal `"Observer reconnecting"` —
    no time-varying token.
  - `reviewing-stalled` pill content: `"Review stalled · {phase}"` —
    `phase` is `state.phase`, sourced from `group.lastPhase`, which is
    a server-published string, stable across ticks within the same
    state.
  Neither pill embeds the tick counter or any wallclock-derived text.
  Each tick re-renders identical DOM text → assistive tech does not
  emit a new announcement per tick. Confirmed.

- **`reviewing-stalled` ARIA role.** Has `role="status"` +
  `aria-atomic="true"` (lines 144-156). Matches the `reconnecting`
  pattern. Single polite announcement on entry. No concern.

- **`StatusPill` exhaustive switch (EC-10).** All 8 named cases land
  in the renderer; the `default` clause has a `never`-assignment that
  compile-fails on a missing variant. Confirmed.

- **`DowngradedChip` exhaustive switch (prior Friedman #19).** All 3
  reasons land in `downgradeReasonHuman`; `default` has the same
  `never`-assignment guard. Confirmed for compile-time. But — the
  user-visible exposure of those 3 reasons is the new finding below.

## NEW Findings

### Finding 1 — DowngradedChip reason hidden from screen-reader users

- **Severity:** P2
- **Files:** `web/src/components/council/FindingsLog.tsx` (lines
  130-140; the `DowngradedChip` component)
- **Real user impact:** Screen-reader user (NVDA, JAWS, VoiceOver
  desktop, TalkBack) using the FindingsLog cannot distinguish *why* a
  STOP was downgraded. The chip's visible text is the literal word
  `"downgraded"`. The three reasons — `evidence_missing_on_disk`
  ("evidence not on disk"), `evidence_not_in_modified_set` ("not in
  modified files"), and the newly-added `wake_version_mismatch`
  ("schema mismatch — review may be stale") — live only inside the
  HTML `title` attribute. `title` is not part of the accessible name
  computation by default; NVDA reads it only when no other accessible
  name is present; JAWS reads it inconsistently; VoiceOver reads it
  after a delay or not at all; TalkBack ignores it. SR users therefore
  hear "downgraded" with no signal whether the observer's evidence is
  missing on disk, not in the change set, or — most importantly under
  this regression pass — that the entire review may be stale from a
  schema mismatch.
- **Why P2 not P3:** The `wake_version_mismatch` reason is
  load-bearing — it tells the user the review is potentially invalid.
  Hiding "review may be stale" behind a hover-only affordance is the
  exact pattern Principle 5 calls out (the screen-reader contract):
  the role is "log" entry, the visible name is "downgraded", the
  reason is silent to AT. Sighted users get the tooltip; SR users get
  a generic word.
- **Recommendation (no code):** Either add the human reason to the
  chip's accessible name (e.g. `aria-label={human}` or visible second
  line for the reason), or co-locate the reason as visible inline
  text — at minimum for `wake_version_mismatch` given its semantic
  weight. Whichever lands, drop a `vitest-axe` + behavioural-AT test
  asserting the chip's accessible name carries the reason text, so
  the next downgrade reason added (the exhaustive switch ensures
  compile-fail in `downgradeReasonHuman`, but does not enforce SR
  exposure).

### Finding 2 — `queued-dropped` pill has no live-region role

- **Severity:** P3
- **Files:** `web/src/components/council/ObserverPanel.tsx`
  (`StatusPill` `case "queued-dropped"`, lines 158-166)
- **Real user impact:** When the server's mid-turn queue supersedes
  one or more checkpoints (Task 4 newest-wins), the pill transitions
  to `"Reviewed (skipped N) · {lastPhase}"`. Sighted users see the
  text change; screen-reader users hear nothing unless they happen to
  navigate to the panel. By comparison, `reconnecting` and
  `reviewing-stalled` both have `role="status"`, so SR users hear
  those transitions politely. `queued-dropped` carries comparably
  important information (the user's checkpoint was skipped, not
  silently lost) and deserves the same announcement channel.
- **Why P3 not P2:** The state is non-blocking — the user is not at
  risk of acting on stale data; subsequent reviews proceed. It is a
  parity gap with the two other transient/notable states rather than
  a hard accessibility blocker.
- **Recommendation (no code):** Add `role="status"` +
  `aria-atomic="true"` to the `queued-dropped` pill div (mirror the
  `reviewing-stalled` block immediately above it). Consider adjusting
  the visible string so the announced text is grammatical when read
  in isolation — "Observer skipped N checkpoints — reviewed
  {lastPhase}" is clearer to an SR user than "Reviewed (skipped N) ·
  {phase}" because the latter relies on the visual `·` separator for
  parse. (UX copy call belongs to Friedman; the a11y ask is the
  announcement channel.)

## Bottom line

Two new a11y findings, both touching information-exposure to
screen-reader users rather than structural correctness:

- **P2** — `DowngradedChip` reason hidden behind `title`-only; the
  newly-added `wake_version_mismatch` ("review may be stale") is
  load-bearing and AT-silent.
- **P3** — `queued-dropped` pill lacks the `role="status"` other
  transient/notable states have; SR users miss the skipped-checkpoint
  transition.

The fix-pass DOES close the cross-mount announcer issue (prior a11y
#10) and DOES close the blank-announce issue (prior a11y #20).
Clock-tick re-render is SR-safe because pill text is stable across
ticks. `StatusPill` and `DowngradedChip` exhaustive switches both
compile-fail on missing variants (EC-10 honoured).
