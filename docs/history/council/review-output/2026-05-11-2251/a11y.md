# Council Review — a11y Auditor

Scope: Phase F Council Mode UI (six new `components/council/*` components + `Sidebar` collapsible-nav additions + archive confirm preview + `use-council-shortcuts`). Prior-floor conventions (AP-1..3, EC-1..9) honoured per `conventions.md`. Axe scans confirmed present on every component test; this review treats axe as the floor and looks above it.

Baseline that is already correct (called out so subsequent reviewers don't drift them):
- Global `:focus-visible` ring + global `@media (prefers-reduced-motion: reduce)` reset shipped in `web/src/index.css` (lines 347–363). All BlockerBanner / CouncilToggle / DegradedBanner animations are governed by this reset — no per-component motion query is required.
- BlockerBanner correctly does NOT `.focus()` itself on mount; the only programmatic focus path is the Cmd/Ctrl+Shift+B opt-in shortcut via `use-council-shortcuts.ts`. The PLAN watchpoint ("Composer is the focus anchor; no async event may call .focus() elsewhere") holds.
- ARIA live-region split is semantically correct: BlockerBanner = `role=alert` + `aria-live=assertive` for content blockers; DegradedBanner = `role=status` + `aria-live=polite` for infrastructure degradation; FindingsLog = `role=log` + `aria-live=polite` on a `<div>` wrapping the `<ul>` (axe `aria-allowed-role` would reject `role=log` on `<ul>`; this is the documented workaround).
- The toggle correctly uses `role=switch` + `aria-checked` (`CouncilToggle.tsx:171–174`).

## P1 — Fix Now

### A11Y-P1-1: CouncilToggle listbox is APG-non-compliant — no keyboard navigation between options

**File**: `web/src/components/council/CouncilToggle.tsx:229–249`
**Principle**: quality-a11y.md → Principle 7 (keyboard navigation), APG `listbox` pattern.

The pairing dropdown opens a container with `role="listbox"` and child `<button role="option">` items. APG's listbox pattern (and what NVDA/JAWS announce when they hear "listbox") mandates Arrow/Home/End/Type-ahead navigation and Escape-to-close. None are implemented:
- No `onKeyDown` handler anywhere in `CouncilToggle.tsx` (confirmed via `Grep onKeyDown|onKeyUp|onKeyPress web/src/components/council/` → zero hits).
- Escape does not close the dropdown — the user has to click outside, which keyboard-only users cannot do without a pointer focus action.
- No `aria-activedescendant` on the listbox, no roving `tabindex` — users must Tab through every option one at a time, while the screen reader announces the listbox as if arrow keys work.
- The trigger has `aria-haspopup="listbox"` (line 207) which announces "menu" expectations to AT users — those expectations are unmet.

Keyboard-only / screen-reader user impact: opens the dropdown, hears "listbox", presses Down arrow, nothing happens. Has to Tab out and re-enter; never discovers that selection works at all. This is a fail-closed a11y gap.

Either: (a) add Arrow/Home/End/Escape/type-ahead, OR (b) drop `role=listbox` + `role=option` and re-cast the dropdown as a `<menu>`/popover where Tab-only navigation is acceptable.

### A11Y-P1-2: ProviderBadges chip text fails WCAG AA contrast against its tinted background

**File**: `web/src/components/council/ProviderBadges.tsx:54–64`
**Principle**: quality-a11y.md → Principle 6 (color contrast — Tailwind defaults are not pre-audited).

The chip palette `bg-cc-primary/10 text-cc-primary` (claude chip) renders the provider name in `--color-cc-primary` (`#d97757`, light mode) over a `cc-primary/10` tint on the `cc-card`/`cc-bg` surface (resolved approx `#faf3ef`). Measured contrast: ~2.8:1. WCAG 2.1 AA body-text floor is 4.5:1; large-text floor is 3:1 (the chip uses `text-[10px]`/`text-[11px]` which is well under "large" by WCAG definition — 10pt is body-text).

Same problem on the codex chip: `text-cc-codex` (`#10a37f`) on `bg-cc-codex/10` is ~3:1 — below 4.5:1 for body text.

Why axe doesn't catch it: axe-core's `color-contrast` rule needs computed background colors. Tailwind's `/10` alpha-modifier produces an `rgba()` over a parent surface that axe can't always resolve when the parent is theme-token-driven. The `toHaveNoViolations()` test on `ProviderBadges.test.tsx:89–101` passes — but the issue is real for low-vision users at any zoom level.

Low-vision / sight-impaired user impact: the very text that identifies the orchestrator/observer half of the pair is the lowest-contrast text on the surface. The ProviderBadges PLAN intent is "asymmetric tinting IS the affordance" (see component doc-comment) — when the tinting itself reduces legibility below WCAG, the affordance becomes inaccessible.

Fix options: use a darker token for the text (the file already defines `--color-cc-primary-btn: #ad5535` and `--color-cc-codex-btn: #0a7d5f` for exactly this reason — they're documented as "Darker button-grade variants — meet WCAG AA (4.5:1)" at `index.css:44–48`), OR increase the chip background alpha (`/25` or higher) to lift the surface contrast.

### A11Y-P1-3: DegradedBanner `text-cc-warning` label fails WCAG AA in light mode

**File**: `web/src/components/council/DegradedBanner.tsx:84`
**Principle**: quality-a11y.md → Principle 6.

The "Observer offline" / "Orchestrator offline" label renders as `text-cc-warning font-semibold` on `bg-cc-warning/8`. Light-mode `--color-cc-warning` is `#b7791f` (gold-brown). Over the `cc-bg` (`#faf9f6`) tinted `~8%` gold surface, measured contrast for the label is ~4.1:1 — under the 4.5:1 AA floor for body text. The body paragraph `text-xs text-cc-fg` uses `--color-cc-fg` (`#141413`) which passes easily; the label itself fails.

Same affects the `Respawn observer` button text inside the banner (line 108): `text-cc-warning` on `bg-cc-warning/15`. Both fail AA.

Dark mode passes (`--color-cc-warning: #f6e05e` on dark surface is ~10:1).

Low-vision user impact: the most-important word on the banner ("offline") becomes the least-legible. axe misses this for the alpha-blended-token reason described in A11Y-P1-2.

Fix: introduce `--color-cc-warning-text` (matching the `cc-primary-btn` / `cc-codex-btn` pattern already in `index.css`) and switch labels / button text inside warning surfaces to use it. Alternatively, use `text-cc-fg` for the label and reserve the gold for the icon and border only.

## P2 — Fix Soon

### A11Y-P2-1: Council component tests assert axe-on-render but skip behavioural keyboard a11y

**Files**: `ObserverPanel.test.tsx`, `BlockerBanner.test.tsx`, `DegradedBanner.test.tsx`, `CouncilToggle.test.tsx`, `FindingsLog.test.tsx`, `ProviderBadges.test.tsx`.
**Principle**: quality-a11y.md → Principle 1 (axe is a floor not a ceiling).

CLAUDE.md mandates `toHaveNoViolations()` — every test file has it. But the same doc says "tests for any interactive behavior (clicks, keyboard shortcuts, state changes)". For council components there are click tests, but no keyboard-only behavioural tests:
- `CouncilToggle.test.tsx`: no test that the switch toggles via `Space`/`Enter`, no test that the listbox responds to arrow keys (related to A11Y-P1-1 — the test wouldn't pass even if written, which is itself the signal), no test for Escape closing the dropdown.
- `ObserverPanel.test.tsx`: no test that the collapse rail expands via Enter/Space (it's a button, so it should — but uncovered).
- `BlockerBanner.test.tsx`: no test that the primary `data-council-blocker-primary` action receives focus via the keyboard shortcut (the shortcut hook is tested in isolation but never against an actual BlockerBanner instance).
- `DegradedBanner.test.tsx`: no test that `Cancel` returns focus to `Respawn observer` after uncontrolled-mode cancel.

axe is a floor — these tests test it. The behavioural a11y above is the ceiling. Pair the axe scan with `userEvent.tab()` / `userEvent.keyboard("{Enter}")` assertions per component so regressions in keyboard flow surface in CI.

### A11Y-P2-2: Status-pill `data-state` changes aren't announced — screen-readers see a silent state transition

**File**: `web/src/components/council/ObserverPanel.tsx:53–104`
**Principle**: quality-a11y.md → Principle 5 (roles and names), Principle 3 (live regions).

`StatusPill` is a plain `<div>` with `data-state={state.name}` and inner text. When the observer transitions sleeping → reviewing → blocker-found, the DOM updates silently. The header is OUTSIDE the FindingsLog's `role=log` live region (FindingsLog is in a different DOM subtree, lines 238–246). The `aria-busy="true"` is on the reviewing pill (line 76) — that helps AT note an async task is running, but it's neither a live region nor a role=status.

Screen-reader user impact: the user sees no indication on the page that their work is being reviewed, that a blocker landed, or that the observer went offline — they have to re-explore the panel to discover the change. The visual pill colour shift is invisible to AT.

Fix: wrap the StatusPill in a `role="status"` + `aria-live="polite"` container (it already has appropriate text per state). Or: emit a separate visually-hidden `role=status` live region beside the pill that announces the new state name on transition. The DegradedBanner already does this correctly — apply the same pattern to status changes inside the panel header.

### A11Y-P2-3: ProviderBadges `role=img` provides per-half attribution but the parent has no role — pairing is announced twice in some readers

**File**: `web/src/components/council/ProviderBadges.tsx:66–96`
**Principle**: quality-a11y.md → Principle 5 (don't duplicate accessible names).

Each Badge is `role="img"` + `aria-label="orchestrator: claude"` / `aria-label="observer: codex"` (line 73–74). The wrapping `<div>` has `aria-label="Pairing: orchestrator claude, observer codex"` (line 89). This produces duplicate semantic content — NVDA reads the wrapper label first, then enters and reads each badge label. The user hears "claude" / "codex" twice in some readers.

The `role=img` on inner badges is also questionable: the chip is text-only ("claude" / "codex" in monospace) — there is no graphical content. `role=img` tells the AT to treat the child text as an image's alt text; "claude" alone is exactly the substring concern flagged in the task brief ("`claude` alone is not enough"). The wrapper's combined label is the meaningful unit — the inner role=img wins nothing here.

Fix: drop `role=img` from each Badge (line 73). Keep the parent wrapper's `aria-label` as the single source of accessible-name truth. The visible text is already readable.

### A11Y-P2-4: CouncilToggle codex-unavailable reason is delivered only via `title` attribute — invisible to keyboard-only users

**File**: `web/src/components/council/CouncilToggle.tsx:97, 105–108`
**Principle**: quality-a11y.md → Principle 5 (form-field labelling), Principle 7.

When `codexAvailable=false`, the codex option has:
- `title={unavailableReason}` (line 97) — only fires on mouseover; keyboard users never trigger this.
- A `<span className="text-[11px] text-cc-muted">{unavailableReason}</span>` inside the option label (line 107) — visible AND announceable when the option is focused. Good.

But also: the option `disabled` attribute is set on a `<button>`. WCAG/ARIA recommend `aria-disabled="true"` over `disabled` for skip-but-still-focusable controls so screen-reader users can hear *why* it's disabled. With `disabled`, the option is not focusable at all — the user tabs past it without ever hearing the reason. The visible reason text is on-screen but unreachable by AT.

Keyboard / SR user impact: a user on Codex-unavailable runs cannot discover why claude+codex is disabled — they tab past, the option is dead, and the visible reason text is the only evidence (and only useful if they happen to mouse-hover).

Fix: replace `disabled={disabled}` with `aria-disabled={disabled}` and gate the `onClick` to `disabled ? undefined : onSelect` (already done on line 98). Then the option is in Tab order and the SR reads "option, disabled, Orchestrator: Claude · Observer: Codex, Codex CLI not detected".

### A11Y-P2-5: BlockerBanner uses `aria-live=assertive` correctly but no shortcut is announced — Cmd/Ctrl+Shift+B is undiscoverable

**File**: `web/src/use-council-shortcuts.ts:5–8`, `BlockerBanner.tsx` (no shortcut surface).
**Principle**: quality-a11y.md → Principle 7 (every shortcut is announced).

`Cmd/Ctrl+Shift+O` and `Cmd/Ctrl+Shift+B` are implemented in `use-council-shortcuts.ts` and tested for behaviour. Neither shortcut is surfaced in the UI — the BlockerBanner has no `aria-keyshortcuts` attribute, no `<kbd>` legend, and no documented shortcut hint. The CouncilToggle similarly hides `Cmd+Shift+O`.

`aria-keyshortcuts="Control+Shift+B"` on the banner root would let screen readers announce "press Ctrl-Shift-B to focus" alongside the alert. The matching pattern is also a discoverability win for sighted keyboard users (e.g., a small `<kbd>` hint inside the banner).

User impact: power users + keyboard-only users + SR users all benefit from shortcuts only when they can discover them. The current implementation rewards users who read the source code.

### A11Y-P2-6: FindingsLog dismiss button is `opacity-0 group-hover:opacity-100 focus:opacity-100` — keyboard-only users can focus an invisible target on first arrival

**File**: `web/src/components/council/FindingsLog.tsx:139–148`
**Principle**: quality-a11y.md → Principle 2 (focus indicators must be visible).

The per-row Dismiss button is `opacity-0` by default. Hover reveals it; `focus:opacity-100` reveals it on focus. But the focus class only fires on the dismiss button itself — Tabbing INTO the row passes through the claim button first (which is full-width). The dismiss button is in the Tab order at full opacity-0 until focus actually lands on it. In practice this works because `:focus` triggers before paint — but it relies on the focus ring being above the `opacity:0` state. Browsers paint focus rings on opacity-0 elements; AT correctly announces them; but the visual focus ring is on a 0-alpha element, which means it's invisible to sighted keyboard users (the ring is rendered, but the underlying button is not — and the ring colour comes from the OS, not the element).

Verify behaviour: open DevTools, Tab through a row. The "×" reveals because `:focus` adds `opacity-100`. Good. But if Tailwind's `focus:` and `group-hover:` cascade differently (e.g., when keyboard focus is on the row container, not the button itself), the button stays invisible.

Fix is small: change `focus:opacity-100` to `focus-visible:opacity-100` AND add `focus-within:opacity-100` on the parent `<li>` so the button reveals as soon as anything in the row is keyboard-focused. Otherwise, sighted keyboard users using Tab to discover dismissable rows hit a moment where the button "vanishes" between row-claim-button-focus and row-dismiss-button-focus.

### A11Y-P2-7: Sidebar archive-confirm Council preview is keyboard-reachable but lacks a focused-on-mount handler — focus stays on the row Archive button which is now obscured

**File**: `web/src/components/Sidebar.tsx:618–671`
**Principle**: quality-a11y.md → Principle 4 (focus management on dynamic UI).

When the confirm preview opens (`confirmArchiveId !== null`), the preview renders at the top of the sidebar with `Cancel` and `Archive pair` buttons. The user reached this state by clicking the row's archive trigger — focus is now on a button that has scrolled out of view (preview pushed content down) or that no longer makes sense to be focused. The preview itself does not auto-focus its `Cancel` button (compare: the delete-modal `<div ref={deleteModalRef} ...>` at lines 925–933 DOES auto-focus its cancel button at lines 363–365).

Keyboard-only user impact: invokes archive, the confirmation appears, Enter is pressed expecting "Cancel" — but focus is still on the row archive button. The user re-fires the archive action by accident, OR has to Tab through every nav button to reach the confirm preview. Same class of bug as the delete modal, fixed there but not here.

Fix: when `confirmArchiveId` flips from null → non-null, `requestAnimationFrame` and focus the Cancel button in the preview. Mirror the lines 363–365 pattern exactly.

## P3 — Consider

### A11Y-P3-1: CollapsedRail uses `[writing-mode:vertical-rl] rotate-180` for the "Observer" label — works visually, fine for AT, but rotated text can be a screen-magnifier pain

**File**: `web/src/components/council/ObserverPanel.tsx:136`

The rail's vertical "Observer" text uses `writing-mode: vertical-rl` + `rotate-180`. Screen readers read it fine (it's just text). Tab key still hits the button. But screen-magnifier users (ZoomText, macOS Zoom) sometimes mis-track the cursor on rotated text. Low-priority — the button itself is large enough to be a hit target. Worth noting only because the panel's PLAN intent is "collapsed rail still shows unread-findings count" — the counter chip is rotation-free, the label is rotated. Consider whether a non-rotated, narrower label would serve users on small viewports better.

### A11Y-P3-2: BlockerBanner `Dismiss for now` button is text-muted by default — visually subordinate to `Open evidence`/`Mark addressed`, but contrast is borderline against the banner background

**File**: `web/src/components/council/BlockerBanner.tsx:112–119`

`text-cc-muted` (`#6f6e69` light) on `bg-cc-error/5` (very light red tint over `cc-card` `#ffffff`) is ~4.3:1 — narrowly below 4.5:1 AA. The button is intentionally subordinate (Friedman's hierarchy decision, not in scope) — but contrast still has to clear AA. Either bump the alpha of the tint, or use `text-cc-fg/70` which renders darker on this surface.

### A11Y-P3-3: ObserverPanel's collapse button has `aria-label="Collapse observer panel"` but the rail's expand button uses a multi-part dynamic label

**File**: `web/src/components/council/ObserverPanel.tsx:117–121, 194`

The collapse button (open state) is "Collapse observer panel". The expand button (collapsed rail) is "Expand observer panel — 2 unresolved blockers" / "Expand observer panel". Mostly fine — but the collapse button should mirror the unresolved-count semantics ("Collapse observer panel — 2 unresolved blockers remain") so a SR user collapsing the panel hears what's about to leave their attention. Polish only.

### A11Y-P3-4: DegradedBanner uses `role=status` + `aria-live=polite` — but on initial mount when the user is mid-task, the announcement may be lost

**File**: `web/src/components/council/DegradedBanner.tsx:71–75`

`aria-live=polite` defers the announcement until the user is idle. On a chat surface where the user is constantly streaming + composing, "idle" rarely happens — the polite announcement may never fire. This is the inverse problem of A11Y-P1's "don't use assertive" — for the degraded case, `polite` may be too quiet. Reasonable as-is given degradation is non-blocking; flag for future telemetry: do users actually notice the banner before glancing at it visually?
