## Findings

### F1 — Integration test asserts visual-channel only; does not exercise the accessible-text channel via accessible queries

**Severity:** P3
**File:** `web/src/glyph-after-reload.test.tsx:213-227`

**Finding.** The new integration test queries the role suffix exclusively via `screen.getAllByTestId("council-role-suffix")` and asserts on `el.textContent`. It never uses an accessible-text query (`screen.getByText(/· orchestrator/i)`, `screen.getByText(/· observer/i)`, or an accessibility-tree query through `*ByRole`). The glyph itself is `aria-hidden="true"` by design — its data-testid is fine as a visual presence assertion because the glyph is purely decorative. But the SIBLING suffix node IS the load-bearing accessible-name carrier for council role; its testid-only assertion treats it as if it were also decoration.

The two channels are semantically distinct and currently happen to live in the same DOM node, but the test cannot tell them apart. If a future refactor wrapped the suffix in `aria-hidden="true"` (a structural anti-pattern Watson explicitly flags — "aria-hidden on a focusable or load-bearing element is the worst kind of accessibility failure", §A ARIA correctness), `el.textContent` would still read the text (DOM textContent is aria-hidden-blind) and the test would still pass. The integration regression that PR #68 is designed to prevent — "council role inaudible after reload" — is itself a screen-reader-channel regression; the test should assert on the channel it is protecting.

**Consequence.** A screen-reader-only failure mode (suffix accidentally hidden from the accessibility tree, or its role-carrying text removed) would not trip the integration test. The post-reload-state regression that the test claims end-to-end coverage of is only covered on the visual axis. The data-testid attribute is also semantically opaque to accessibility tooling — it cannot tell anyone what the screen reader will actually announce.

**Fix.** Add a parallel assertion using an accessible query alongside the testid query. Use `screen.getByText` with regex matching ` · orchestrator` and ` · observer` (case-insensitive, exact suffix shape), or assert via `screen.getAllByRole("button", { name: /· orchestrator/i })` if the Sidebar row exposes a button role for the session entry. Keep the testid query as the visual-presence canary; add the accessible-text query as the screen-reader-channel canary. Both must hold for the integration test to honour its end-to-end claim. No source change to ProjectGroup or SessionItem is needed — the existing markup already supports both queries; the test simply does not exercise one of them.

### F2 — ProjectGroup.tsx receives a behavioural prop delta but ships without a sibling .test.tsx file

**Severity:** P2
**File:** `web/src/components/ProjectGroup.tsx:13-18, 120-123`

**Finding.** `ProjectGroup.tsx` is a `web/src/components/` file whose `getCouncilInfo` callback signature was widened in this PR to include `role`, with the role then plumbed through to `SessionItem` as a new `councilRole` prop. Per CLAUDE.md ("**Every new or modified frontend component** in `web/src/components/` **must** have an accompanying `.test.tsx` file with at minimum: a render test, an axe accessibility scan (`toHaveNoViolations()`), and tests for any interactive behaviour"), the component-modification trigger fires here — but `web/src/components/ProjectGroup.test.tsx` does not exist in the repository (verified by file lookup; no entry in `git diff --stat`).

The new integration test `glyph-after-reload.test.tsx` covers the store → Sidebar → SessionItem reactive chain that PASSES THROUGH ProjectGroup, but it does not exercise ProjectGroup's contract in isolation. Specifically: it does not assert that ProjectGroup correctly forwards `council.role` when present and omits it when undefined; it does not run axe at the ProjectGroup boundary; and it does not catch a future refactor that drops the new `councilRole` spread (the exact bug class this PR exists to fix in the opposite direction).

The accessibility consequence is structural rather than direct — ProjectGroup itself adds no ARIA — but a missing component-level test for a touched component means the next regression in this prop-forwarding layer would only be caught at integration level, where failures are slower to diagnose and where the test surface is larger.

**Consequence.** Future edits to ProjectGroup that silently drop the `councilRole` spread (same bug class this PR closes) would not trigger a component-scoped failure. The behavioural contract that "given `getCouncilInfo` returns a role, that role reaches SessionItem" is enforced only transitively through one integration test. The CLAUDE.md test-mandate gate, which is the operational form of WCAG operationalization (§B), has a documented exception in this PR scope that should be closed before merge or explicitly tracked as a follow-up.

**Fix.** Add `web/src/components/ProjectGroup.test.tsx` with: (a) a render test with a mock `getCouncilInfo` returning `{role: "orchestrator", pairing: "claude+codex"}` and an assertion that SessionItem receives the role (verified through the rendered glyph/suffix testids), (b) the symmetric observer case, (c) the `getCouncilInfo` returns `undefined` case (the regression canary — confirms the glyph/suffix branch is skipped), (d) a `toHaveNoViolations()` axe scan on the rendered output. Alternatively, if scope-of-PR pressure makes the new test file out-of-bounds, file a tracked follow-up task and annotate the absence in the PR body. Do not let the gap normalize.

The CLAUDE.md test mandate fires on "every new or modified frontend component" — this is a useEffect inside an existing component, not a new component, and it produces no UI. The accessibility consequence is null.

**Consequence.** None. The fetch failure mode is silent on the UI; live WebSocket pushes remain the resilience path. The screen-reader audience experience is unchanged (group records that fail to bootstrap simply leave the Sidebar in its pre-PR-#68 state, with neither glyph nor suffix — the same as for solo sessions).

**Fix.** None required. Confirmed for completeness of the audit scope.

### F4 — Glyph + suffix pattern is preserved end-to-end for active-session pairs (the previously-broken case)

**Severity:** P3 (informational — confirmation of correct pattern preservation)
**File:** `web/src/components/SessionItem.tsx:260-280` (consumer); `web/src/components/ProjectGroup.tsx:123` (producer delta)

**Finding.** The glyph + suffix accessibility pattern (decoration via `aria-hidden="true"` plus a sibling plain-text suffix carrying the role as accessible-name content) is the correct §A ARIA-correctness pattern: decorative imagery gets `aria-hidden="true"` so the screen reader skips it; the role information is announced once via the sibling text node, not twice. The contract was already correct in `SessionItem.tsx`; the bug was upstream — ProjectGroup never PASSED `councilRole` down for active sessions, so the conditional `{councilRole && ...}` branches in SessionItem never rendered for the live (non-bootstrap) path. The PR's plumb-through restores the contract for the active-session case.

End-to-end behaviour after this PR for the previously-broken case: active orchestrator/observer pairs now render the ☼/☽ glyph (decorative) and the " · orchestrator"/" · observer" suffix (accessible). Screen-reader users hear the session label followed by " · orchestrator" or " · observer" without the glyph character being announced; sighted users see the glyph as a quick visual delimiter.

**Consequence.** Positive. The accessibility contract that previously held only for the bootstrap-replay path (the synthetic-hydration code path from PR #61) now also holds for the live-creation path. The audience that depends on the role suffix being announced (screen-reader users distinguishing orchestrator from observer rows) is now served on every entry to the Sidebar.

**Fix.** None required. Confirmed for the audit record.
