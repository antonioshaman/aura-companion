# Council Mode (paired orchestrator + observer sessions)

> Moved out of `CLAUDE.md` in P2/A3 (2026-09-28). `CLAUDE.md` links here with one line;
> this file is loaded on demand, not on every session start.


A user-opt-in flag on the New Session form (`councilMode: "council"` + `councilPairing: "claude+claude" | "claude+codex"`) spawns two linked CLI sessions sharing one workspace — an **orchestrator** that the user drives via the main chat surface, and an **observer** that wakes on filesystem checkpoint sentinels, reads a manifest of paths, replies with a bare findings array (the server builds and writes the review file — P3/B1), and the server fans grounded findings back into the orchestrator's UI as `BlockerBanner` + side-panel `ObserverPanel`.

**Cross-process protocol** lives entirely on the filesystem under `<workspace>/.council/`:
- `.council/prompts/observer-system.md` — versioned (`<!-- observer-system-prompt v1 -->`) CLI-agnostic role definition. Loaded at observer spawn time; hash stamped on `SdkSessionInfo.observerPromptSha256`. **OPTIONAL per-workspace override** — if absent, the bundled fallback (`observer-prompt-bundled.ts`, generated from this repo's canonical artifact) is used and `SdkSessionInfo.observerPromptSource` reflects `"bundled"` vs `"workspace"`. Malformed-but-present STILL throws — the explicit-intent contract is preserved at the loader layer.
- `.council/prompts/OBSERVER-SOUL.md` — the observer's identity (core truths / boundaries / vibe), versioned `<!-- observer-soul v1 -->`, CLI-agnostic and portable between the claude and codex halves (handoff 2026-10-18 §4, from `specs/lifeos-and-soul-md-takeaways.md`). It is NOT loaded on its own: `bun run build-observer-prompt-bundle` splices its body between the `soul:begin` / `soul:end` markers of `observer-system.md` (pure `web/scripts/observer-soul-splice.ts`), so the loader, the `v1` header contract, the bundled fallback and the recorder's prompt hash are unchanged. Edit the SOUL, run the build; the CI drift gate covers both files.
- `.council/checkpoints/<phase>.json` — written by the orchestrator via `writeAtomicJson` after each Carmack-Council phase. Schema: `CheckpointPayload` in `council-types.ts`. Producer-side REST: `POST /api/sessions/:id/council/checkpoint` with the JSON payload as the body — server validates via `parseCheckpointPayload`, cross-checks `session_group_id` against the caller's actual group (orchestrator-half only), then atomically writes into the workspace's `.council/checkpoints/` directory.
- `.council/reviews/<phase>-<session_group_id>-<provider>-observer.md` — written by the **server** since P3/B1 (`observer-reply.ts`): on the observer's `observer:turn-done` the host extracts the findings array from its final message, stamps the envelope from host facts (checkpoint identity from the dispatched wake, server clock, provider from the pairing, model from the observer's frames, CLI version from init), validates it with `parseObserverReviewPayload` and `writeAtomicJson`s it. An unusable reply writes nothing and logs `council.observer_reply.rejected`; one bad reply disarms the wake→review watchdog, three in a row (`OBSERVER_REPLY_REJECTIONS_BEFORE_DEGRADE`) or silence let it degrade the group as before. Transition: an observer still on the pre-B1 prompt writes the file itself (any legacy name the watcher accepts) and the host stands down. Content is JSON despite `.md` extension. Filename MUST carry the `<provider>` segment (`claude` | `codex`) so the `claude+codex` pairing produces two distinct review files per checkpoint rather than colliding under the watcher's debounce window.

**Server pipeline:**
1. `routes.ts /sessions/create` (or `/sessions/create-stream`) branches on `councilMode === "council"` → `orchestrator.createCouncilGroup`.
2. `SessionGroupCoordinator` calls injected spawn callback twice (orchestrator + observer) with shared `sessionGroupId` and respective `sessionGroupRole`. Atomic rollback — observer-spawn failure kills the orchestrator half before propagating.
3. `cli-launcher.applyCouncilObserverSpawnConfig` loads the prompt artefact, applies `getObserverSpawnOverrides()` (allowed/disallowed tools + permission mode intersected with caller-supplied lists), and injects `--append-system-prompt` (Claude) or `systemPrompt` option (Codex).
4. `council-lifecycle.startCouncilWatchers` (via `session-orchestrator`) arms `watchCheckpoints` + `watchReviews` on the workspace's `.council/` subtree (recursive `mkdirSync` ensures the dirs exist before watch attach).
5. Steps 5–6 live in `council-checkpoint-pipeline.ts` (`CouncilCheckpointPipeline`, extracted from the orchestrator in P4/C1a; the orchestrator owns the watcher/meta maps and injects them). On each checkpoint: `handleCouncilCheckpoint` rejects stale sequences, captures the prior checkpoint, emits `group:checkpoint`.
6. On each review file: `handleCouncilReview` runs `validateObserverFindings` against the manifest's delta paths (via `buildObserverContextManifest`); STOPs outside the modified set OR missing on disk are downgraded to NOTE server-side. Findings get deterministic `fnd_<hex>` ids derived from `(sessionGroupId, checkpointId, observerProvider, findingIndex, evidence_path, claim)` — restart-replay produces stable ids, browser dedup catches it. Emits `group:review` with both findings + downgrades.
   Then (P3/B2b, `observer-disputes.ts`) every live STOP is matched against the group's disputes in `.council/state/<group>-disputes.json`: a STOP whose normalised claim equals a disputed one, or that quotes the same distinctive code span (a backticked command, or a span of ≥ 12 chars), gets `disputed: "same_claim" | "shared_anchor"`. It stays a STOP in the findings log with a "dismissed earlier" chip but never raises the banner or the unread counts. Disputes are written only by the server, from `POST /api/groups/:groupId/disputes`, which the browser calls when a human dismisses a STOP. The observer cannot write `.council/state/`. Log events: `council.finding.disputed`, `council.finding.dispute_matched`.
   Wakes that bypass the live watcher (restart catch-up scan, the EC-13 5-min failsafe tick, the watcher re-arm scan, the spawn-checkpoint poll) live in `council-observer-scheduler.ts` (`CouncilObserverScheduler`, P4/C1b); every wake still goes through the pipeline's `dispatchObserverWake`.
   **Observer auto-heal (P4/OBS-AUTOHEAL, `council-observer-autoheal.ts`).** When the observer's backend adapter is gone (a live wake skipped with `adapter_missing`, or a catch-up poll timing out), the scheduler relaunches the OBSERVER half only — at most 2 attempts per episode (0 s / 30 s backoff), at most 4 relaunches per group per rolling hour, one episode at a time — waits up to 60 s for the adapter to attach and re-sends the missed wake. The pair is degraded only when that budget is exhausted (a rate-limited heal falls back to the 3-strike threshold). No heal when the user stopped either half or an intentional kill is in progress (EC-2, P4/KILL-INTENTIONAL). EC-9 log events: `observer.autoheal.attempt` / `.ok` / `.exhausted` / `.skipped` / `.rate_limited` / `.relaunch_failed`. Same for Claude and Codex observers. The heal relaunch shares the per-session single-flight gate with every other relaunch path (see session-lifecycle.md) and does not reset the auto-relaunch crash budget. The hourly budget is in memory: a server restart resets it (at most 4 more relaunches per group per restart). With auto-heal, an observer that never attaches degrades the pair after about 3 min (30 s poll + 2 × 60 s attach wait + 30 s backoff), not after ~15 min of 3 failsafe strikes as before; a rate-limited heal keeps the old 3-strike path.

   **Silent / unanswered wake recovery (W14, `observer-wake-silence.ts`, `council-wake-recovery.ts`).** A wake turn that delivers no inbound frame for `OBSERVER_WAKE_SILENCE_MS` (default 120 s, env `COMPANION_OBSERVER_WAKE_SILENCE_MS`, bounded to [30 s, 270 s]; healthy codex wake turns never gap more than ~35 s) is treated as lost (codex: while a `commandExecution` item is open the window widens to 2×, since a quiet command emits nothing until it completes). Codex: the adapter interrupts the silent turn and re-sends the same wake once on a FRESH thread (`council.observer_wake_silent.retried`, bus `observer:wake-retried` re-arms the review deadline); a second silence, or a fresh `thread/start` that fails (deaf transport), emits `observer:wake-failed` with `reason: "silent"`. Claude: a wake with zero output in that window emits the same event (no in-process retry — the relaunch is the retry). A silent report or an expired review deadline degrades the pair with `wake_produced_no_review`, re-queues the newest owed checkpoint in the pending slot and starts the observer auto-heal with trigger `wake_produced_no_review` (allowed on a `degraded` pair; the self-recovered shortcut is honoured only after a relaunch that returned ok — a failed or thrown attempt never counts; waits for a still-streaming wake turn to end first). The relaunch handshake (`half_respawned` / `reconnect_ok`) drains the slot. While a pair is `degraded`, arriving checkpoints are queued (newest-wins) instead of dropped. EC-9 events: `council.observer_wake_silent`, `council.wake.redelivery_queued`, `council.observer_wake_recovery.start` / `.deferred` / `.done`.
   **Budget guard (`council-budget.ts`).** Every council half's `result` frame is accounted per pair (and per role) in tokens — Claude `result.usage`, Codex usage normalised to the same shape by `codex-turn-usage.ts` (Codex collab-subagent completions carry none; `total_cost_usd` is not used because Codex reports 0). Budgeted tokens = input + output + cache-creation of both halves; cache reads are tracked and shown but **not counted** (they are 95–99 % of prompt tokens on long sessions and cheap). Limit: env `COMPANION_COUNCIL_MAX_TOKENS_PER_GROUP` (default **20 000 000**, `0` disables, a malformed value keeps the default and logs `council.budget.limit_invalid`). The default is ~7× the heaviest single session in 30 days of prod `llm.turn_usage` (2.85 M over 41 turns), and stops a runaway loop (~2 M/h) within ~10 h. When the spend since creation / last Continue crosses it, the server stops **automatic activity only**: observer wakes (pipeline gate `budget_exceeded` — the checkpoint is queued newest-wins, not dropped; this also covers the EC-13 failsafe and catch-up wakes), the W15 second opinion (`council.second_review.skipped` reason `budget_exceeded`) and auto-proceed (a pending idle timer is cancelled, re-arming is refused: `auto-proceed.budget-exceeded`). No process is killed and no running turn is interrupted; the user can keep chatting with the orchestrator. EC-9: `council.budget.exceeded` (sessionGroupId, sessionId + role of the half whose turn crossed, spent/limit). Browsers of both halves get a `group_budget` frame (`exceeded` / `continued`, full snapshot); the findings bootstrap carries `budget` for reloaded tabs; the ObserverPanel shows `CouncilBudgetNotice` with a per-role breakdown and **Continue** → `POST /api/groups/:id/budget/continue` `{ limitTokens? }` (restarts the spend window, optionally sets a pair-specific limit, `0` = no guard for this pair; delivers the queued checkpoint and re-arms auto-proceed if the orchestrator is idle; logs `council.budget.continued`). `GET /api/groups/:id/budget` returns the snapshot. State is persisted write-through in `.council/state/<group>-budget.json` (server-written, observer cannot write there), so a restart does not hand a looping pair a fresh budget. No loop detector — the token cap is the backstop.
7. `wireGroupListeners` in `initialize()` fans `group:created` / `group:exited` / `group:degraded` / `group:checkpoint` / `group:review` out to both halves' browsers via `wsBridge.broadcastToGroup`.
8. `applyEvent` on the coordinator's state machine is the **sole** lifecycle mutator: a pure `deriveSideEffects(prev, next, event)` table decides which `group:*` bus events fire and which EC-9 log entries land; `applyEvent` drains both. `archiveGroup` routes through `applyEvent({type:"user_archived"})` so the `group:exited` emit comes from the same channel, still firing BEFORE the kills proceed so the browser cleans its store first.
9. Unintentional `session:exited` against a council-tracked half drives `coordinator.armReconnect` (45s grace, env-overridable via `COMPANION_GROUP_RECONNECT_GRACE_MS`) instead of immediate `group:degraded`. If the half re-handshakes via `session:cli-id-received` within the window → `reconnect_ok` → `group:created` re-broadcast (active). Otherwise → `reconnect_failed` → `group:degraded`. `relaunchExhaustedNotified` or `intentionalKills` short-circuit the grace; cascading second-half death also short-circuits. EC-2 invariant is preserved on the kill paths (archive/delete still mark both intentional first).

**Browser pipeline:**
1. `ws.ts` switch dispatches `group_*` / `observer_review` to council slice actions.
2. `observer-panel-state.deriveObserverPanelState` derives the discriminated-union status from `(group, findings, dismissedStopIds)` — priority ladder degraded > blocker-found > reconnecting > reviewing > spawning > sleeping > never-checkpointed-yet.
3. `BlockerBanner` renders the most-recent unresolved STOP in the same DOM slot as `PermissionBanner` (permission-first stacking); `ObserverPanel` (sibling of ChatView) renders the status pill + collapsible rail + FindingsLog; `Sidebar` shows per-session ProviderBadges + unread STOP counter.
4. `useBrowserTitleAlert` prepends `(N)` to `document.title` aggregated across all groups; `useCouncilShortcuts` provides `Cmd/Ctrl+Shift+O` (toggle panel) and `Cmd/Ctrl+Shift+B` (focus blocker primary action).

**Convention floor** (AP-1..3, EC-1..9, EC-13 — do not re-flag in council reviews): kept in the
core `CLAUDE.md` under "Council Mode convention floor" so reviewers always load it; not duplicated here.

Full conventions list in `conventions.md`. Council review artefacts (per-expert findings + synthesised `FINAL-REVIEW.md`) in `.council/review-output/<TIMESTAMP>/`.
Archived process history (closed handoffs, plans, bug write-ups, past council batches) lives in `docs/history/` — see `docs/history/README.md`. It is history, not current rules: never treat it as a source of active conventions.

**Convergence counter is a streak, not a verdict (P3/CONV-HONEST).** `convergence-tracker.ts` folds only STOP-free reviews in which the host saw the observer read ≥1 changed file of the checkpoint (`observer-read-ledger.ts`, fed by the observer's `message:assistant` tool_use frames — Claude `Read`/`Grep`/`Bash`, Codex `commandExecution` → `Bash`). Spawn/empty checkpoints and reviews with no reads emit `not-counted` (counter unchanged; UI shows "not counted: …"). A STOP always resets. The UI says "N reviews in a row without blockers" with a not-a-readiness-guarantee tooltip — never "ready to ship". Threshold (default 3, range 2–5) is unchanged.

**Observer rigor (2026-10-16).** (1) The wake names the language claims must be written in (`observer-language.ts`: `COMPANION_OBSERVER_CLAIM_LANGUAGE=ru|en|auto`, else the user's recent orchestrator messages, else the prose artifacts); identifiers stay verbatim. (2) No re-wake for an answered checkpoint: `findFreshOwnReview` (pipeline Gate 0b `already_reviewed`, and the catch-up scan's `council.wake.restart_catchup_skipped_reviewed`) treats an own review on disk that postdates the checkpoint's `emitted_at` as the answer — the wake sentinel is cleared on every degrade/exit, so it alone cannot dedupe across restarts. An `OBSERVER-BLOCKED`-only review does not count. Gate 0a `wake_in_flight` skips a second wake for the checkpoint whose review is still owed. (3) An empty review whose turn read nothing beyond the prose artifacts (`touchesReachBeyondArtifacts`) is written with `host_verification: "unverified"`, shown as "не проверено" and not counted toward convergence (`unverified_clean`); the prompt's "Verify before you pass" rule asks the observer to open every cited `file:line` on closure checkpoints. (4) Liveness probes (`[liveness probe] …`, `observer-probe.ts`) are not review traffic: a wake is queued (`probe_in_flight`) while a probe turn runs, a wake turn ending in probe prose is a `probe_turn` (no review, no rejection strike), and the observer feed renders probe exchanges as collapsed rows. (5) `GET /api/groups/:id/findings` returns `checkpointCoverage` (`checkpoint-coverage.ts`); the panel lists never-reviewed ("без ревью") and unverified ("не проверено") checkpoints, kept current by live frames.

**Second opinion — multi-model review (W15, `second-reviewer.ts`, `second-reviewer-config.ts`).** A pair can add a second, read-only reviewer on another backend/model next to its observer (two models catch different real bugs). Setting: `reviewer: "off" | "auto" | {backend, model?}` + `scope: "review-implement" (default) | "all"`; `auto` = the backend opposite the observer (codex observer → `claude` on the `sonnet` alias; claude observer → `codex` default model). Per pair: `.council/state/<group>-second-reviewer.json` (server-written from the create body `secondReviewer`/`secondReviewScope` or `PUT /api/groups/:id/second-reviewer`; the observer cannot write `.council/state/`), else the global Settings default `councilSecondReviewer` (default off). Mechanism = **one-shot headless run per in-scope checkpoint, not a second observer session**: no spawn/heal/reconnect/degrade lifecycle to duplicate, and a failed run can never degrade the pair. On each live checkpoint the pipeline calls `onCheckpointAccepted` after the observer's wake; the runner (one run per group, newest-wins 1-slot queue, hard timeout `COMPANION_SECOND_REVIEW_TIMEOUT_MS` default 10 min, per-backend cooldown after a usage-limit answer, skip while any session on that backend sits in a usage limit) runs `claude -p --tools Read,Grep,Glob --permission-mode dontAsk --strict-mcp-config …` or `codex exec --sandbox read-only …` with the same observer system prompt + wake text, extracts the findings array (`extractObserverFindings`), host-stamps the envelope with `reviewer_role: "second"`, writes `.council/reviews/<phase>-<group>-second-<provider>-observer.md` and hands the payload straight to `handleCouncilReview` (the per-group watcher skips that name so it is never ingested twice). Every reader that means "the observer answered" (reply capture, Gate 0b, deadline rescan, coverage) ignores `reviewer_role: "second"`; a second review never touches the observer's watchdog, read ledger or `lastReviewedCheckpointId`. Findings get ids in their own namespace (`<provider>#second`), carry `reviewer: {role, provider, model}` (live and REST bootstrap) and show a model badge; a near-identical claim the other reviewer already raised (same file, overlapping lines, Jaccard ≥ 0.5, not more severe) is marked `duplicateOf` and folds into that row ("also flagged by …") and never holds/banners on its own. A STOP from either reviewer raises the banner and holds auto-proceed. Convergence (`group:second-review` bus event): when a second review was dispatched for a checkpoint, the observer's clean review is held (`not-counted: awaiting_second_review`) and folds only once the second opinion is clean too; a second-opinion STOP resets the streak; a failed/limited/superseded one leaves the checkpoint `second_review_missing`. Hardening (review round 1): the CLI gets an allowlisted env only (`buildSecondReviewEnv`: PATH/HOME/locale/TERM + `CODEX_HOME` for codex, Claude's own auth vars for claude — never COMPANION_*/AURA_* or API keys); codex also gets `-c sandbox_workspace_write.network_access=false` (the read-only sandbox already has no network — verified: `curl` → "Could not resolve host"); runs are spawned in their own process group and a timeout/abort kills the group; at most `COMPANION_SECOND_REVIEW_MAX_CONCURRENCY` (default 2) runs at once process-wide, the rest wait newest-wins per pair and are announced to the tracker as owed (`queued`) at once; "codex, default model" pins the first slug of `$CODEX_HOME/models_cache.json` (the config default can be unlaunchable). Dedupe compares FINAL verdicts (frozen grounding) and never folds a blocking STOP into a non-blocking one. Logs: `council.second_review.{dispatched,completed,skipped,failed,queued,ingested}` with sessionGroupId, checkpointId, backend, model.
