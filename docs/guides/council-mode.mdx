# Council Mode

Council Mode pairs your main agent (the **orchestrator**) with an independent **observer** session that wakes on every phase checkpoint, reads only the just-changed surface, and pushes grounded findings back into your chat. The multi-agent pattern that worked manually in past pipelines — catching a couple of P1 issues per phase that single-author review missed — is reproducible in one click instead of two terminals.

<img src="../screenshots/council-mode-overview.png" alt="Council Mode showing orchestrator chat alongside the observer panel surfacing a STOP finding" width="100%" />

## What the observer is — and isn't

The observer is an LLM. It can hallucinate, miss real defects, and over-flag stylistic noise. A `STOP` finding is a prompt to **look**, not a verdict to obey; the user is the final judge of every finding. The grounding gate described below keeps findings honest about the files they reference, but it does not — and cannot — make the observer's *judgement* correct. Calibrate trust accordingly.

## What the observer can and cannot do

**Can:**

- Read the manifest delta of the most recent checkpoint (just-changed files).
- Emit findings against those files only.
- Run again on the next checkpoint, fresh.

**Cannot:**

- Write to your workspace. The write boundary is enforced at spawn argv (tool allow-list + permission mode).
- Reach files outside the checkpoint manifest. Server-side grounding gate downgrades any STOP that strays.
- Persist memory across phases. Each wake is independent — the observer reads only the current checkpoint's delta vs the previous, via `buildObserverContextManifest`.
- Run your tests, execute code, or see your conversation with the orchestrator beyond what landed in the checkpoint.

## When to use it

Turn Council Mode on when you want a second pair of eyes on a Carmack-Council pipeline (`/spec-writer → /council-plan → /council-implement → /council-review → /test-architect`). The observer is most valuable for:

- Multi-step refactors where one wrong invariant in step 3 corrupts everything downstream.
- Security-sensitive code paths (auth, permission gates, write boundaries).
- Test specs — the observer often catches missing negative ACs or vacuously-passing assertions.

Leave it off for trivial one-shot fixes; the overhead of two sessions and the BlockerBanner ceremony is not worth it.

## Enabling Council Mode

On the **New Session** dialog:

1. Toggle **Council Mode** on.
2. Pick a provider pairing in the dropdown that appears:

| Pairing | Behaviour | When to pick |
|---|---|---|
| **`claude+claude`** (default) | Two Claude Code sessions sharing one workspace. Symmetric tooling, same model family. | Default. Lowest friction. |
| **`claude+codex`** (experimental) | Orchestrator on Claude, observer on Codex. Cross-model independence — different reasoning pass on the artefacts. | When you want correlated-failure-mode resistance: two Claudes tend to echo each other's blind spots (same training distribution, similar refusal patterns), while a Codex observer can surface issues a Claude observer would rationalise past. Cost: asymmetric tooling, separate billing, and the observer prompt is currently tuned on Claude. |

3. Click **Start**. The backend spawns two linked sessions sharing one `sessionGroupId`, one workspace (single git worktree), and identical env/permissions.

<Note>
If the observer-side provider has no working credentials, the launch is rejected with an inline error naming the missing credential — no half-paired session is created. The orchestrator never starts alone.
</Note>

## ObserverPanel states

The status pill in the panel header is in exactly one of seven states. The priority ladder ("top wins") is encoded by the order below:

1. `degraded` — observer process died and has not been respawned. Orchestrator continues; manual respawn available.
2. `blocker-found` — at least one unresolved STOP.
3. `reconnecting` — observer's CLI subprocess is reconnecting after a transport blip.
4. `reviewing` — observer is mid-pass on the latest checkpoint.
5. `spawning` — initial boot — system prompt loaded, CLI not yet ready.
6. `sleeping` — all clear. No unresolved findings.
7. `never-checkpointed-yet` — observer is up but the orchestrator has not written a first checkpoint, so there is nothing to review yet.

## How findings get grounded

Every observer finding is checked against the modified surface of the checkpoint that triggered the review. STOPs only reach the BlockerBanner when they reference real, just-changed files. STOPs whose `evidence_path` is **not** in the checkpoint's `modifiedFiles` set, or which does not exist on disk, are **downgraded to NOTE** server-side. The observer's write boundary is enforced at the spawn argv (tool allow-list + permission mode intersected with caller config).

### Worked example

1. You write code and the orchestrator records a checkpoint listing `modifiedFiles: ["web/server/foo.ts"]`.
2. The observer wakes, reads the delta, and emits two findings:
   - **STOP** with `evidence_path: "web/server/foo.ts"` — claim about a real change.
   - **STOP** with `evidence_path: "web/server/bar.ts"` — claim about a file that didn't change this checkpoint.
3. The server runs `validateObserverFindings`:
   - First STOP survives → wrapped and broadcast as a BlockerBanner.
   - Second STOP is downgraded to NOTE (out-of-delta), recorded with a downgrade reason, broadcast for audit only.
4. The browser renders the surviving STOP in the BlockerBanner slot and lists both findings in the FindingsLog — the demoted one tagged `DOWNGRADED` with the reason visible.

You see exactly what the observer claimed and exactly what the server did with it; nothing is silently suppressed.

## Finding lifecycle

A finding moves through four user-visible states:

- **Raised** — STOP reaches the BlockerBanner; the FindingsLog row is unread.
- **Resolved** — you address the underlying issue and dismiss the banner; FindingsLog row stays for audit.
- **Downgraded** — the grounding gate demoted a STOP to NOTE before it reached the banner; visible only in FindingsLog with the demotion reason.
- **Archived** — the session closes; findings persist on disk for post-hoc review.

## Restart-replay determinism

Findings carry deterministic `fnd_<hex>` ids derived from `(sessionGroupId, checkpointId, observerProvider, findingIndex, evidence_path, claim)`. If the observer crashes after writing a review file and the orchestrator restarts, the same review file re-processed produces the same finding ids; the browser dedupes so you don't see duplicates. **What is deterministic:** the id, given identical inputs. **What is not:** the claim text — re-running the observer on the same checkpoint may yield differently-worded claims (LLM non-determinism) and therefore different ids.

## Provider badges (sidebar)

Each session row in the sidebar shows provider chips. For a `claude+claude` pair, you see one symmetric chip. For `claude+codex`, you see two asymmetric chips so the active billing source is visible at a glance.

## Degraded mode

If the observer process dies (crashed, manually killed, ran out of credit), the orchestrator continues — your work is never blocked by an observer fault. The Observer panel status pill flips to **`degraded`** and a **DegradedBanner** appears in the panel header.

To recover:

1. Open the Observer panel.
2. Click **Respawn observer** in the DegradedBanner.
3. The backend re-spawns the observer half with the same workspace, system prompt, and group id. State resumes from the most recent checkpoint on disk.

If respawn keeps failing, pull the observer's recording at `~/.companion/recordings/` and filter by `sessionGroupRole=observer` — the JSON-RPC handshake errors are the most common signal (missing credential, model unavailable for the chosen provider).

## Workspace artefacts

While Council Mode runs, the workspace gets a `.council/` subtree:

```
.council/
├── prompts/
│   └── observer-system.md      # Optional per-workspace override; bundled fallback fires on ENOENT
├── checkpoints/
│   └── <phase>.json            # Orchestrator writes after each Carmack phase
├── reviews/
│   └── <phase>-<provider>-observer.md   # Observer writes (content is JSON despite .md)
└── review-output/<TIMESTAMP>/  # Per-expert findings + synthesised FINAL-REVIEW.md
```

The `<provider>` filename segment is contract surface — a `claude+codex` pairing produces two distinct review files per checkpoint without colliding under the watcher's debounce window.

You can commit these artefacts — they're useful for post-hoc review and reproducible Council debugging.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| ObserverPanel stuck on `spawning` | Observer CLI failed to boot — credential missing OR the workspace's `.council/prompts/observer-system.md` is present-but-unreadable (`EACCES` / `EISDIR` / `ELOOP`). `ENOENT` does NOT block spawn — the bundled fallback fires and logs `council.observer-prompt.bundled-fallback`. | Verify the observer-provider credential. If a workspace override exists, check `chmod`/`stat`. To intentionally use the bundled prompt, delete the workspace override. |
| BlockerBanner never appears even after a phase | Observer's STOP `evidence_path` didn't land in `modifiedFiles` (all STOPs downgraded to NOTE — visible in FindingsLog as `DOWNGRADED`). | Confirm in the FindingsLog. Widen the checkpoint manifest if your phase legitimately touches files outside the modified set. |
| Status pill flips `reviewing → sleeping` with no findings | Observer ran to completion but had nothing to flag — this is the happy path. | No action. Phase is clean. |
| Two STOPs on the same finding | Stale browser state from a server restart before the dedup id landed. | Hard-refresh; the deterministic `fnd_<hex>` will collapse them. |
| `claude+codex` pairing produces one review file, not two | Observer wrote to the wrong filename or the watcher debounced two writes. | The filename **must** include the `<provider>` segment — this is the contract; if your observer is custom, ensure it writes `<phase>-codex-observer.md`, not `<phase>-observer.md`. |
| Wrote a checkpoint and no review for >5 min | Observer is alive but missed the event (rare — `fs.watch` edge / macOS dirname quirk). | Wait one more failsafe cycle: a recurring 5-minute scan reconciles unprocessed checkpoints. Worst-case observer latency is bounded by this tick. |
| Suspicious-looking finding ("did the observer just hallucinate?") | LLM judgement nondeterminism. | Pull the observer recording at `~/.companion/recordings/` (filter by `sessionGroupRole=observer`), find the JSON-RPC frame around the review-file write — the raw observer output, the `modifiedFiles` set, and the grounding-gate decision are all there. Recordings are the ground truth for any disputed finding. |

## Limits in v1

- The Carmack chain is not auto-invoked — you still type each skill explicitly. Council Mode just adds the observer; it doesn't drive the orchestrator.
- Only pairs (N=2) — no triads.
- No cross-session shared memory during a phase; the only protocol is the filesystem under `.council/`.
- Observer system prompts cannot be hot-swapped mid-session.
- Codex observer is optional, not mandatory; Codex stays an experimental adapter.
