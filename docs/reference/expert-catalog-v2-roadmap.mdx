# Expert Catalog v2 Roadmap

This page is the canonical reference for the **v2 expert catalog** for Council Mode. **Phase 3α/β are complete** — all 22 seats live on the `feat/council-v2-pipeline` branch with EC-34 wire-format (`paired_with` + `tension_axis`) codified. **v1 remains the production default** until atomic-swap promotion at the end of Phase 6 (see [council-experts-catalog-v2-expansion.md](https://github.com/antonioshaman/aura-companion/blob/main/specs/council-experts-catalog-v2-expansion.md) spec for full architecture).

For the user-facing Council Mode guide, see [Council Mode](/guides/council-mode). For the wire protocol and state machine, see [Council Mode Architecture](/reference/council-mode-architecture).

## Why a v2 catalog at all

**v1** seated councilors by **domain tag** — `a11y-expert`, `backend-expert`, `frontend-react-expert`, `deploy-devops`, `subprocess-expert`, etc. Two structural problems surfaced over time:

1. **LLM dispatch ambiguity.** Domain names collide with prose-level verbs and noun-classes in user briefs; "deploy this" or "this is a frontend issue" looks identical to LLM routing as the expert-tag itself. Subagent dispatch consequently routes inconsistently.
2. **Coverage gaps invisible to count.** "14 experts" reads complete; "no observability expert seated" hides until a production incident makes it visible. Expanding domain-coverage by adding tags doesn't surface design tension — it just stacks lenses.

**v2** rebases the catalog on **real-person surnames**: each expert is an actual engineer with a published body of work whose lens we want represented. The rename is operationally driven (LLM dispatch reliability via proper-noun disambiguation; willison REC-4 in Phase 2 council plan output), but it also surfaces design intent — each name carries a recognisable philosophy you can compare against the alternative.

## Phase 3β — 8 seated as ideological-tension pairs

The original Phase 3 expansion plan (Lerdorf for PHP + Colvin for pydantic-ai) was rescoped after a key user insight (`specs/external-knowledge-enrichment-sources.md` Section F): **catalog growth past ~12 seats should add ideological tension, not domain coverage.**

The rationale: a council of 12 domain experts produces parallel non-overlapping findings → synthesis is list-aggregation. A council of paired experts on shared domains, where each pair disagrees on philosophy, produces conflicting findings → synthesis is **resolution**. Carmack-chair arbitrates the tension based on project economic context.

Council seating logic per task: the chair picks **which pairing** is active based on stack-detection signals, not the full catalog. Multi-pairing membership is fine — Fowler's published body of work crosses both axes.

**Anti-pattern boundary (operator-explicit):** the catalog target is **not** "100+ agents". Per user guidance documented in `external-knowledge-enrichment-sources.md`: _"7-15 strong allies + routing + shared memory + human approval + context compression. 10x value vs '159 agents ради агентов' (token furnace, zombie agents, context hell)."_ Phase 3β lands at 22 seats — well within the strong-allies envelope when chair-side stack-detection seats a subset (typically 7-12) per task.

## Phase 3γ — chair-side stack-detection

A separate workstream codifies the chair selecting **which subset** of the 22-expert catalog to seat per task. Inputs at dispatch time:

- Project anchors (`package.json` / `composer.json` / `pyproject.toml` / `Cargo.toml` / etc.) — determines stack
- Brief content (security-sensitive vs UI-only vs schema-migration) — determines lens emphasis
- Per-task tension axis selection — chair picks which paired-tension is active for THIS task

Phase 3γ is **not** part of Phase 3α/β implementation work; it's a downstream chair-logic refactor that uses the post-3α/β catalog as input. See `specs/council-experts-catalog-v2-expansion.md` Phase 3 section.

## EC-34 — ratified

Codified in `conventions.md` after Phase 3β closure:

> **EC-34** — Expert seating by ideological tension, not domain coverage. Multi-expert councils at scale (>12 seats) should pair experts on each domain by orthogonal-philosophy axis (purity-vs-pragmatism, principle-vs-economics, paranoia-vs-curiosity). Synthesis becomes resolution, not aggregation. Carmack-chair filter picks based on project economic context. Wire-format: `paired_with` + `tension_axis` fields in each expert's `meta.yaml`; legacy 2-key entries retro-populated.
