# Council Mode Architecture

This page is the technical reference for Council Mode. For the user-facing guide, see [Council Mode](/guides/council-mode).

## High-level data flow

```
You ──── orchestrator chat ────► orchestrator CLI ────► writes .council/checkpoints/<phase>.json
                                                                      │
                                                       (atomic write: tmp + rename + fsync)
                                                                      ▼
                                              checkpoint-watcher (fs.watch + debounce + LRU dedup)
                                                                      │
                                                                      ▼
                                                       observer CLI reads manifest delta
                                                                      │
                                                                      ▼
                                              writes .council/reviews/<phase>-<provider>-observer.md
                                                                      │
                                                                      ▼
                                              review-watcher → validates STOPs against modifiedFiles
                                                                      │
                                                                      ▼
                                              wsBridge.broadcastToGroup → both halves' browsers
                                                                      │
                                                                      ▼
                                              orchestrator UI: BlockerBanner + ObserverPanel
```

The entire cross-process protocol lives on the filesystem under `<workspace>/.council/`. There is no shared memory, no IPC socket, no RPC. The watcher debounce + atomic-write contract is what makes this race-free.

## Filesystem protocol

### `.council/prompts/observer-system.md`

CLI-agnostic role definition with a versioned marker (`<!-- observer-system-prompt v1 -->`). Loaded at observer spawn; SHA-256 stamped on `SdkSessionInfo.observerPromptSha256` so you can correlate observer behaviour with the exact prompt revision.

This file is **optional** per workspace. If absent (`ENOENT`), the loader falls back to the BUNDLED artefact in `observer-prompt-bundled.ts`, auto-generated from this repo's canonical `.council/prompts/observer-system.md`. Provenance is stamped on `SdkSessionInfo.observerPromptSource: "workspace" | "bundled"` and surfaced via a WARN log `council.observer-prompt.bundled-fallback` when fallback fires. **Other error classes still throw**: `EACCES` / `EISDIR` / `ELOOP` on the workspace file are explicit-intent failures, not silently bypassed.

#### Auditing observer behaviour across runs

Three fields together give you a stable audit trail per observer session:

- `observerPromptSha256` — exact prompt content hash. Same hash across two sessions ⇒ comparable findings; different hash ⇒ expect drift even on identical code.
- `observerPromptSource` — `"workspace"` if the per-workspace override loaded, `"bundled"` if the in-repo fallback fired.
- The `council.observer-prompt.bundled-fallback` WARN log — fires once per bundled-fallback event with the workspace path; grep this when reconciling "why does my workspace prompt seem ignored."

### `.council/checkpoints/<phase>.json`

Written by the orchestrator after each Carmack-Council phase via `writeAtomicJson` (`atomic-write.ts`). Schema lives in `web/server/council-types.ts` as `CheckpointPayload`:

```json
{
  "sessionGroupId": "grp_…",
  "checkpointId": "ckpt_…",
  "phase": "council-implement",
  "sequence": 3,
  "createdAt": "2026-05-12T…Z",
  "modifiedFiles": ["web/server/ws-bridge.ts", "…"],
  "manifestPaths": ["web/server/…", "…"]
}
```

`sequence` is a monotone counter — stale checkpoints (older sequence than the current) are rejected by `handleCouncilCheckpoint`.

### `.council/reviews/<phase>-<provider>-observer.md`

Written by the observer. Content is JSON despite the `.md` extension — the extension keeps it grep-friendly alongside other markdown artefacts. **The filename MUST carry the `<provider>` segment** (`claude` | `codex`) so the `claude+codex` pairing produces two distinct review files per checkpoint rather than colliding under the watcher's debounce window. This is non-negotiable contract surface.

Schema (`ObserverReviewPayload` in `council-types.ts`):

```json
{
  "checkpointId": "ckpt_…",
  "observerProvider": "claude",
  "findings": [
    {
      "severity": "STOP",
      "claim": "…",
      "evidence_path": "web/server/ws-bridge.ts",
      "evidence_lines": [42, 47]
    }
  ]
}
```

## Group state machine

The single source of truth for group lifecycle is `web/server/group-state-machine.ts` — a pure `transition(state, event)` function over five states:

| State | Meaning | Out-edges |
|---|---|---|
| `pairing` | Both halves spawning; not yet ready. | → `active` on both-ready; → `archived` on spawn-rollback. |
| `active` | Both halves alive and connected. | → `degraded` on one-half death; → `archived` on intentional kill. |
| `degraded` | One half (usually observer) is gone; orchestrator continues. | → `active` on respawn; → `archived` on user archive. |
| `reconnecting` | Transport blip; CLI subprocess is mid-reconnect. | → `active` on reconnect; → `degraded` on timeout. |
| `archived` | Terminal. Both halves killed, persistence flushed. | (none) |

All transitions go through `applyEvent` on the `SessionGroupCoordinator`, which emits one of these bus events for `wireGroupListeners` to fan out:

- `group:created` — when `createCouncilGroup` succeeds.
- `group:exited` — emitted directly by `archiveGroup` **before** the kills, so the browser cleans its store before the signal lands.
- `group:degraded` — on unintentional half-death; observer `respawnObserver` returns this to `active`.
- `group:checkpoint` — on each new checkpoint write.
- `group:review` — on each new review file write, with findings + downgrades.

## Convention floor

Council Mode is constrained by the AP- (architecture-pattern) and EC- (edge-case) conventions ratified in [`conventions.md`](https://github.com/antonioshaman/aura-companion/blob/main/conventions.md) at the repo root. Reviewers MUST NOT re-flag violations of these as new findings unless the convention itself is being changed.

`conventions.md` is the authoritative, evolving list — currently spanning `AP-1..AP-4` and `EC-1..EC-33` (with gaps at EC-13 and EC-25..EC-29 reserved for future entries). The most load-bearing entries for the architecture below:

- **`AP-2`** — `group-state-machine.ts` is the single source of truth for group lifecycle status.
- **`AP-3`** — `council-types.ts` hosts both writer and reader schemas in one file.
- **`EC-1`** — Observer SDK permission profile is applied at spawn argv (`applyCouncilObserverSpawnConfig`).
- **`EC-2`** — Group-aware kills mark BOTH session ids intentional BEFORE either kill executes.
- **`EC-4`** — Filesystem watcher debounce never silently coalesces distinct payloads. Key by `(file, mtimeNs)` and log `onDropped("superseded")`.
- **`EC-6`** — Load-bearing protocol parsers require replay-based regression tests.
- **`EC-7`** — Filesystem-access predicates inline path resolution OR are exposed only via a resolving wrapper.
- **`EC-12`** — `fs.watch`-driven pipelines require an explicit pre-scan reconcile on initialize (the observer failsafe: scan `.council/checkpoints/` for unprocessed entries on startup and synthesise wakes; bounds worst-case observer latency).

For rationale and the complete AP- / EC- enumeration, follow the link above — `conventions.md` is the canonical reference; this page deliberately does not restate it.

## Grounding gate (server-side)

When a review file lands, `handleCouncilReview` runs `validateObserverFindings`:

1. Parse the review payload against `ObserverReviewPayload`.
2. For each `STOP`, resolve `evidence_path` via `realpath` (per `EC-7` — inlined in the wrapper, never bare).
3. If the resolved path is **outside** the checkpoint's `modifiedFiles` set OR not present on disk, **downgrade the STOP to NOTE** and record the downgrade reason.
4. Wrap surviving STOPs via `wrapObserverFindingForInjection` and broadcast as `group:review` with both the surviving findings and the list of downgrades for audit.

This is the single point where "observer claims X" becomes "user sees a BlockerBanner about X." The grounding gate is a quality control — it keeps findings honest about the files they reference. It is not a security guarantee against an adversarial orchestrator with filesystem write access to the same workspace; the observer's *judgement* (what is and isn't a real defect) remains an LLM property.

## Observer write boundary

The observer is permitted to read code but not to modify it. The boundary is enforced at spawn time, not at runtime:

- `applyCouncilObserverSpawnConfig` (`cli-launcher.ts`) injects the observer-specific tool allow-list and permission mode at the CLI argv (per `EC-1`).
- `observer-permissions.ts` declares the allow / deny lists; a module-load canary asserts the sets are disjoint.
- `observer-write-policy.ts`'s `assertObserverWriteAllowed(path, root)` resolves `realpath` and bounds-checks against the workspace root before any write the observer might attempt.

A failure to keep these three pieces in agreement is a regression of `EC-1`; do not paraphrase the contract — the conventions floor is the source of truth.

## Restart recovery

`group-reconciliation.ts` runs at server boot and inspects each persisted group's two halves against currently-alive PIDs:

| Live status | Action |
|---|---|
| Both alive | Reattach WebSockets; state stays `active`. |
| Orchestrator only | Mark group `degraded`; observer respawn available. |
| Observer only | Treat orchestrator as the source of truth — relaunch orchestrator with `--resume`; observer reconnects to the relaunched group id. |
| Neither | Group archived during downtime; persistence reflects that. |

Sentinel-before-sweep (per `EC-8`) means the reconciliation marks intentional kills **before** any signal is sent, so the proactive-relaunch listener does not race.

## Browser pipeline

1. `ws.ts` switch dispatches `group_*` / `observer_review` frames to council slice actions.
2. `observer-panel-state.deriveObserverPanelState({group, findings, dismissedStopIds, nowMs})` derives the discriminated-union status from inputs. Priority ladder: `degraded > blocker-found > reconnecting > reviewing > spawning > sleeping > never-checkpointed-yet`.
3. `BlockerBanner` renders the most-recent unresolved STOP in the same DOM slot as `PermissionBanner`. Permission requests stack first — the user must clear permissions before addressing the blocker.
4. `ObserverPanel` (sibling of ChatView) renders the status pill + collapsible rail + FindingsLog.
5. `Sidebar` shows per-session `ProviderBadges` + an unread-STOP counter.
6. `useBrowserTitleAlert` aggregates unresolved STOP counts across all groups and prepends `(N)` to `document.title`.
7. `useCouncilShortcuts` wires `Cmd/Ctrl+Shift+O` (toggle panel) and `Cmd/Ctrl+Shift+B` (focus blocker primary action).

## Authorization

`group-authorization.ts` issues a cryptographic group-id pattern at create time and requires it on all council-scoped REST endpoints. The Companion auth token still gates access globally; the group id is a second factor that prevents one browser tab in a multi-user environment from accidentally targeting another tab's group.

## Recordings

Council Mode emits no special recording stream — both halves use the standard recorder (`web/server/recorder.ts`) writing to `~/.companion/recordings/`. Each half's recording carries its `sessionGroupId` and `sessionGroupRole` in the header so you can correlate the two streams when reconstructing a session post-hoc. For a disputed finding, the recording is the ground truth: it contains the raw observer JSON-RPC output, the `modifiedFiles` set the observer was given, and the grounding-gate decision.
